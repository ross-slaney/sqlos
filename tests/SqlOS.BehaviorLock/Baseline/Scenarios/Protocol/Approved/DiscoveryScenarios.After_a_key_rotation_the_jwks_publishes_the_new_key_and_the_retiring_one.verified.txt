# SqlOS behavior lock transcript
scenario: DiscoveryScenarios.After_a_key_rotation_the_jwks_publishes_the_new_key_and_the_retiring_one
profile: hosted

## 1. resource-server: one key before the rotation
> GET /sqlos/auth/.well-known/jwks.json
< 200 OK
< Content-Type: application/json; charset=utf-8
    {
      "keys": [
        {
          "alg": "RS256",
          "e": "AQAB",
          "kid": "{kid#1}",
          "kty": "RSA",
          "n": "{token#1}",
          "use": "sig"
        }
      ]
    }

## 2. operator: the operator rotates the signing key
> POST /sqlos/admin/auth/api/signing-keys/rotate
> Content-Type: application/json; charset=utf-8
> X-BehaviorLock-Operator: behavior-lock-operator
>   {}
< 200 OK
< Content-Type: application/json; charset=utf-8
    {
      "activatedAt": "{datetime:utc-z}",
      "algorithm": "RS256",
      "id": "{key#1}",
      "kid": "{kid#2}"
    }

## document: the new key and the retiring key are both published (GET /sqlos/auth/.well-known/jwks.json -> 200 application/json; charset=utf-8; keys in first-seen order)
    {
      "keys": [
        {
          "kty": "RSA",
          "use": "sig",
          "alg": "RS256",
          "kid": "{kid#1}",
          "n": "{token#1}",
          "e": "AQAB"
        },
        {
          "kty": "RSA",
          "use": "sig",
          "alg": "RS256",
          "kid": "{kid#2}",
          "n": "{token#2}",
          "e": "AQAB"
        }
      ]
    }

# A token signed before the rotation and one signed after it: the kid in each header names the key that signed it.
