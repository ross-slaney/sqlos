# 8.0 baseline metrics

[`scripts/domain-metrics.sh`](../../scripts/domain-metrics.sh) measures how far SqlOS is from a rich domain model: entity state any caller can set, lifecycle writes spread across services, persistence and audit calls, clock reads, long methods, large classes, wide constructors and duplicated flows. This page defines each metric and records the baseline on `25fb3f0` (SqlOS 7.2.1). Tasks 2 to 5 of the 8.0.0 refactor (#436 to #439) report their deltas against these values. The script is the source of truth; this page is its specification. [Sign-in latency](#sign-in-latency) records the other baseline the refactor reports against: how long sign-ins take on 7.2.1 and on the refactored source.

## Run it

```bash
scripts/domain-metrics.sh                   # key=value, one metric per line, fixed order
scripts/domain-metrics.sh --json            # the same keys, in the same order, as one JSON object
scripts/domain-metrics.sh --root <checkout> # measure another checkout
```

The script needs only bash and python3, runs on macOS and ubuntu-latest, reads the source without building it, finishes in about a second and prints the same output for the same tree.

To report a delta, measure the base and the change with the same copy of the script:

```bash
git worktree add ../sqlos-base <base-commit>
scripts/domain-metrics.sh --json --root ../sqlos-base > before.json
scripts/domain-metrics.sh --json > after.json
diff before.json after.json
```

A layer that changes a counting rule updates this page and re-measures the base with the new rule, so every reported delta compares like with like.

## What is scanned

Every `*.cs` file under `src/SqlOS`, excluding `bin/` and `obj/`. Before matching, the script blanks comments, preprocessor lines and the text of string and character literals (regular, verbatim, raw and interpolated), and keeps the code inside interpolation holes. SQL inside strings and XML-doc `cref`s never count. A `_files` key is the number of files with at least one site. Line counts are physical lines.

## Definitions

| Keys | Counting rule |
|---|---|
| `entity_classes`, `entity_settable_properties` | An entity is a distinct type `T` passed to `Entity<T>` in a `*ModelConfiguration.cs` file, that is, every type the EF model maps. A settable property is a public, non-static property declared in the entity class with a `set` or `init` accessor that has no `private`, `protected` or `internal` modifier. Navigation properties count; fields do not. |
| `revoked_at_write_sites`, `revoked_at_write_files`, and the same pair for `is_active`, `consumed_at`, `is_verified` | A write site is a member-access assignment to the property with any assignment operator (`x.RevokedAt = now`, `x.RevokedAt ??= now`) or an EF bulk update `SetProperty(x => x.RevokedAt, …)`. The receiver type is not checked. Comparisons, lambdas and declarations are not writes. Object-initializer members (`new SqlOSUser { IsActive = true }`) are not counted: they set construction values, and a text rule cannot tell an entity initializer from a DTO projection such as `IsActive = x.IsActive`. |
| `authorization_request_assignment_sites`, `authorization_request_assignment_files` | An assignment, with the operators above, to a settable property of `SqlOSAuthorizationRequest` through an identifier that the same file types as one: a parameter, local or field declared as `SqlOSAuthorizationRequest`, or a `var` initialized from `new SqlOSAuthorizationRequest`, from a `Set<SqlOSAuthorizationRequest>()` query ending in `First`, `Single`, `Last` or `Find` (with or without `OrDefault` and `Async`), or from a call to a method declared in `src/SqlOS` to return `SqlOSAuthorizationRequest`, bare or in a `Task` or `ValueTask`. Object initializers are not counted. |
| `save_changes_call_sites`, `save_changes_call_files` | Invocations of `SaveChangesAsync(`. Method declarations (the two interface members and the `SqlOSDbContext` overrides) are excluded. |
| `audit_write_sites`, `audit_write_files` | Each product-code call site that records an audit event, counted once. The sinks are `new SqlOSAuditEvent` and `RecordAsync(` on a receiver whose name contains `audit` (`SqlOSAuditLogService`). An audit helper is a method outside `src/SqlOS/AuditLogs` whose name or declaring type contains `Audit` and whose body reaches a sink or another helper. On 7.2.1 there are 16 helper names, such as `RecordAuditAsync`, `RecordPortalAuditAsync`, `AuditAsync`, `AddAuditEvent`, `AddDeniedAudit` and `RecordIfDiagnosticAsync`. The count is sink occurrences plus helper invocations, excluding declarations and anything inside a helper body or inside `src/SqlOS/AuditLogs`, which is plumbing. |
| `datetime_utcnow_uses` | Occurrences of `DateTime.UtcNow` in code, including interpolation holes. `DateTimeOffset.UtcNow` and `TimeProvider` are not counted. |
| `methods_over_100_lines` | Methods, constructors and local functions, block-bodied or expression-bodied, that span more than 100 lines from the first line of the declaration (after attributes) to the closing `}` or `;`. Lambdas, accessors and operators are not methods. |
| `largest_class_lines`, `largest_class` | The largest non-static class, record or struct by lines, summing all of its `partial` declarations, each from its declaration line to its closing brace. Nested types count toward the outer type. Static classes are excluded because they hold extension methods: the static partial `EndpointRouteBuilderExtensions` spreads endpoint mapping across 22 files. |
| `largest_file_lines`, `largest_file` | The `*.cs` file with the most lines (newline count, as `wc -l`), with its repository path. |
| `max_constructor_parameters`, `max_constructor_parameters_class` | The most parameters declared by one constructor, including class primary constructors, and its class. Positional record parameters are properties and are excluded. Ties go to the first class name in ordinal order. |
| `duplicated_flow_<flow>_services` | For each flow below, the number of distinct classes whose name ends in `Service` and that *implement* the flow: they declare a public or internal method whose whole name matches the flow pattern and whose body does not hand the flow to process code. Process code is every type in a `*.Processes.*` namespace: a process (a class that declares `ExecuteAsync`), invoked through its constructor or the factory method named after it, or a step the processes share (a static class there), invoked through one of its methods. A method that only calls forwarding methods of its own class (an overload) forwards too. Each method is judged on its own body, so a forwarding overload never excuses an implementing one. A public facade or a surface's adapter that forwards keeps its 7.x signature but is an entry point, not an implementation, and does not count; the process is the flow's one implementation, so a flow that only its process implements reads 0 (layer 2 changed this rule, see [Counting rule changes](#counting-rule-changes)). |

| Flow key | Method name pattern | Classes on 7.2.1 |
|---|---|---|
| `signup` | `SignUp\w*Async` | `SqlOSAuthService`, `SqlOSAuthorizationServerService`, `SqlOSHeadlessAuthService` |
| `mfa_verify` | `(Verify\|Complete)\w*Mfa\w*Async` | `SqlOSAuthService`, `SqlOSAuthorizationServerService`, `SqlOSHeadlessAuthService` |
| `email_otp_verify` | `(Verify\|Complete)\w*EmailOtp\w*Async` | `SqlOSAuthService`, `SqlOSHeadlessAuthService` |
| `magic_link_complete` | `(Verify\|Complete)\w*MagicLink\w*Async` | `SqlOSAuthService`, `SqlOSHeadlessAuthService` |
| `organization_select` | `(Select\|Complete)\w*Organization\w*Async` | `SqlOSAuthService`, `SqlOSAuthorizationServerService`, `SqlOSHeadlessAuthService` |

## Counting rule changes

**Layer 2 (#436): duplicated flows count implementations.** Until layer 2 the key counted entry points: every service that declared a method named for the flow, so a public facade that kept its 7.x signature (as §3.8 of the [design record](domain-model.md) requires) counted the same as a copy of the flow, and the key could never fall while the facades stayed. The rule now leaves out a method that hands the flow to process code. A process is one class per use case (§3.7), so what the key still counts is a service that implements the flow itself, next to or instead of its process: a duplicate. Applied to the 7.2.1 baseline, and to the base of layer 2 (`0aaac32`), the new rule gives the values the old rule gave, 3, 3, 2, 2 and 3, because nothing forwarded to a process yet; the reported deltas compare like with like.

| Flow key | 7.2.1 (`25fb3f0`) | Layer 2, after sign-in and sign-up processes (`390abac`) | Layer 2 delivered |
|---|---|---|---|
| `signup` | 3 | 0 | 0 |
| `mfa_verify` | 3 | 3 | 0 |
| `email_otp_verify` | 2 | 0 | 0 |
| `magic_link_complete` | 2 | 0 | 0 |
| `organization_select` | 3 | 3 | 3 |

Organization selection is not an identity flow: choosing the organization a login continues in is the authorization-server hub's step (§15 Amendment 4), and layer 3 (#437) models it in the authorization request's state machine.

## Limits

- The rules are lexical. Apart from `SqlOSAuthorizationRequest` receivers, no types are resolved, so the four lifecycle properties count on any receiver.
- An identifier typed as `SqlOSAuthorizationRequest` anywhere in a file is treated as one throughout that file.
- An audit helper without `Audit` in its name or declaring type counts as one sink site, and its callers do not count.
- Duplicated flows are matched by method name. A method that hands the flow to process code does not count, whatever transport parsing and outcome mapping it does around that call; a copy of a flow under a method name the patterns do not match is not seen at all.

## Sign-in latency

Issue #436 requires a password and email-code sign-in latency benchmark whose before and after numbers show no meaningful regression. [`tests/SqlOS.Benchmarks.SignIn`](../../tests/SqlOS.Benchmarks.SignIn/SqlOS.Benchmarks.SignIn.csproj) is that benchmark, and [`scripts/sign-in-benchmark.sh`](../../scripts/sign-in-benchmark.sh) runs it. Layers 3 to 5 re-run it against the same 7.2.1 baseline. It is a project of its own, beside the FGA benchmark in `tests/SqlOS.Benchmarks`, because it builds against SqlOS as source or as the released package, so nothing in it may reference `src/SqlOS` directly.

### Run the benchmark

```bash
scripts/sign-in-benchmark.sh --mode package --build-only     # build both flavors first
scripts/sign-in-benchmark.sh --mode source --build-only
scripts/sign-in-benchmark.sh --mode package --no-build       # SqlOS 7.2.1 from NuGet, SQL Server
scripts/sign-in-benchmark.sh --mode source --no-build --provider postgresql --accounts 100000
scripts/sign-in-benchmark.sh --compare --steps --sql TestResults/SignInBenchmark/<runs>/*.json
```

Each mode builds into `artifacts/sign-in-benchmark/<mode>`, so both flavors coexist and the solution's `bin/` output is untouched. A run starts its own database server with the Aspire app host (Docker), or uses `--server "<connection string>"`. It writes every sample to `TestResults/SignInBenchmark`, with the SQL of one sign-in per scenario and each statement's time per sign-in. `--compare` prints runs side by side as Markdown, one table per provider and account count. `--sql` ranks the statements whose time per sign-in changed most between the first build named and the last. `--label` names a build, which two builds of one commit need. The benchmark is not part of pull-request CI, because shared runners are too noisy for timings. Run it on a quiet machine, one run at a time: where other agents share the machine, hold its test mutex while a run measures.

### Method

- **Four sign-ins, end to end.**
  - `password`: a first-party client's direct password sign-in (`POST /sqlos/auth/password/login`).
  - `email-code`: an account's first email-code sign-in. The client starts it (`POST /sqlos/auth/email-otp/start`), reads the code from the email the host's fake captured, and verifies it (`POST /sqlos/auth/email-otp/verify`). The code also proves and claims the unverified address the operator created the account with.
  - `email-code-returning`: the same requests for an account whose address an earlier email-code sign-in verified, which is what most sign-ins are.
  - `hosted`: the hosted round trip. A browser opens an authorization request's password page (`GET /sqlos/auth/authorize`) and posts the form with the page's CSRF cookie and token (`POST /sqlos/auth/login/password`), then the client redeems the code with PKCE (`POST /sqlos/auth/token`).

  Every request must succeed or the run stops, so no error path is timed.
- **One harness, both builds.** The flows drive `tests/SqlOS.BehaviorLock.Host`, in its `hosted` profile, over HTTP and in-process (TestServer runs the whole ASP.NET Core pipeline) against a real database. The host references SqlOS as source or as the 7.2.1 package (`-p:SqlOSUnderTest`), and the behavior lock's guard stops a run whose loaded `SqlOS.dll` is not the build it asked for.
- **Isolation.** Every measured sign-in has an account of its own, created through the admin API before anything is measured, and comes from a client address in `198.18.0.0/15`, the range reserved for benchmarks, that no other request used. No lockout or admission bucket carries over from one sign-in to the next. Each returning account signs in once with a code during setup, and the run then waits out the 30-second resend cooldown. The run changes one option: the shared client's hourly email-code limit (`MaxChallengesPerClientPerHour`, 300 by default) is raised so that all of a run's codes are admitted.
- **Account count.** By default the database holds only the run's own 2,004 accounts. `--accounts N` first writes N more straight into the user, email and credential tables, each with a verified address and a password. Nothing signs them in. They make a query that reads one account's rows by an unindexed column scan as many rows as it would in a deployment of that size.
- **Warm-up and order.** Each scenario runs 100 unmeasured sign-ins, then one traced sign-in (its SQL is recorded), then 400 measured ones. Scenarios interleave round-robin, one sign-in of each per round, so drift on the machine affects them alike. The heap is collected before measuring starts. The in-process host runs with the server garbage collector, as ASP.NET Core hosts do.
- **Timing.** A request is timed from when it is sent until its body has been read, and a sign-in's latency is the sum of its requests. Parsing the page and reading the email between requests are the client's work and are not timed.
- **Statistics.** The mean, p50, p95 and p99 per scenario and per request, with percentiles interpolated between ranks (type 7). Far outliers, above Q3 + 3 × IQR, are counted and kept.
- **Database work.** The benchmark counts the commands each sign-in sends at the ADO.NET provider, so the rate-limit store's raw commands count too, and sums their time. It profiles each statement's executions and time per sign-in, and records the bytes allocated per sign-in (approximate) and the cost of one password comparison. Both builds use ASP.NET Core Identity's PBKDF2, so that cost is the same in each.
- **Runs.** Each build runs twice per provider, ordered so that linear drift on the machine cancels: package, source, source, package (with a third build: A, B, C, C, B, A). Every run is a new process, container and database. A run counts only if the machine's 1-minute load average was at most 8 when measuring started and when it ended. A run above that is repeated, and every run's files are kept.

### Results

PostgreSQL with 100,000 background accounts, 400 measured sign-ins per scenario. The table uses the quietest run of each build, with load average under 8. The full set is under `TestResults/SignInBenchmark/scale-100k-final`. "Layer 2" is `4f88ceb` plus schema version 48 (BL-0009). Without those indexes, layer 2 measured 91–99 ms p50 for `password`, from the scans described in BL-0009.

| Scenario | 7.2.1 p50 | Layer 2 p50 | 7.2.1 p95 | Layer 2 p95 | SQL commands (7.2.1 → layer 2) |
|---|---:|---:|---:|---:|---:|
| `password` | 80.2 ms | 73.6 ms | 84.1 ms | 78.0 ms | 46 → 47 |
| `email-code` | 50.8 ms | 45.5 ms | 55.7 ms | 50.0 ms | 56 → 59 |
| `email-code-returning` | 33.6 ms | 36.9 ms | 37.8 ms | 41.7 ms | 42 → 45 |
| `hosted` | 103.9 ms | 96.8 ms | 109.7 ms | 103.2 ms | 75 → 75 |

The returning email-code sign-in sends three more commands than 7.2.1 and is about 10% slower at p50. Layer 2's process rework (§15 Amendment 7) removes those extra reads. The benchmark is re-run on both providers once that rework lands.
