# 8.0 behavior ledger

The 8.0.0 refactor ([#435](https://github.com/ross-slaney/sqlos/issues/435)) rebuilds SqlOS's internals without changing what hosts, users, operators, directories, and client applications observe. The behavior lock in `tests/SqlOS.BehaviorLock` records that observable behavior as approved files, and every layer of the refactor is judged against them.

This ledger is the only way an approved file may change during the refactor. A pull request that modifies or deletes an approved file must add an entry here that names the file and explains why the new behavior is intended. Reviewers read the approved-file diff and its entry together: the diff shows exactly what changed, and the entry says why that change is acceptable.

## Approved files

- `tests/SqlOS.BehaviorLock/**/*.verified.txt`: scenario transcripts (`Scenarios/<Area>/Approved`), the public API approval (`PublicApi`), and the schema approvals (`Schema`).
- `packages/headless/tests/__snapshots__/*`: the `@sqlos/headless` public surface snapshot.

Adding an approved file is new coverage and needs no entry. Modifying or deleting one needs an entry. Renaming one without changing its content needs no entry.

## Rules

1. A pure refactor never changes an approved file. If a refactor changes one, it changed behavior: fix the refactor, or justify the change here.
2. Every entry has one category:
   - **defect fixed**: the old behavior was wrong (a security gap, a spec violation, a crash, data loss, or a documented contract the code did not keep).
   - **DX improvement**: the old behavior worked but was harder to integrate, configure, operate, or diagnose than it needs to be.
   - **maintainability improvement**: an observable detail that only existed because of internal structure, such as the order of an unordered list, an error message wording, or a generated name.
3. Every entry links the issue that tracks the change, so the release notes and the migration guide can find it.
4. An entry lists every approved file it justifies by its repository-relative path in backticks. One entry may cover several files.
5. Entries are append-only. Never reuse or renumber an ID. To revise a decision, add a new entry that references the old one.
6. `scripts/check-behavior-ledger.sh` enforces rules 2 to 5 on every pull request. It fails when an approved file is modified or deleted without being named on a line the pull request adds to this ledger, and when an entry is missing a field.
7. The baseline job runs the behavior lock against the released 7.2.1 package. It skips approved files listed here, because they describe intended 8.0.0 behavior that 7.2.1 does not have, and it still checks everything else.

## Entry format

    ### BL-0001: One-line summary of the behavior change

    - **Approved files:** `tests/SqlOS.BehaviorLock/Scenarios/Example/Approved/ExampleScenarios.Example_scenario.verified.txt`
    - **Category:** defect fixed
    - **Justification:** What changes, for whom, why the old behavior was wrong or worse, and why no host needs to change code (or what it must change).
    - **Issue:** #NNN

Headings are `### BL-` followed by a four-digit number and a colon. The four fields are required, one per line, in any order. Add entries under **Entries** in ID order.
