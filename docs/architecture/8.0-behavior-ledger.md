# 8.0 behavior ledger

The 8.0.0 refactor ([#435](https://github.com/ross-slaney/sqlos/issues/435)) rebuilds SqlOS's internals without changing what hosts, users, operators, directories, and client applications observe. The behavior lock in `tests/SqlOS.BehaviorLock` records that observable behavior as approved files, and every layer of the refactor is judged against them.

This ledger is the only way an approved file may change during the refactor. A pull request that modifies or deletes an approved file must add an entry here that names the file and explains why the new behavior is intended. Reviewers read the approved-file diff and its entry together: the diff shows exactly what changed, and the entry says why that change is acceptable.

The behavior lock keeps two records of every scenario. The **baseline** (`tests/SqlOS.BehaviorLock/Baseline`) is every approved file exactly as it was when the lock matched the released 7.2.1 package, and it never changes: it is 7.2.1's behavior, and the package job holds the released package to it on every pull request. The **current** approved files beside the scenarios are 8.0's behavior. This ledger is the difference between the two, justified: `scripts/check-behavior-baseline.sh` fails unless its entries name exactly the approved files that differ from their baseline.

## Approved files

- `tests/SqlOS.BehaviorLock/**/*.verified.txt` outside `Baseline/`: scenario transcripts (`Scenarios/<Area>/Approved`), the public API approval (`PublicApi`), and the schema approvals (`Schema`).
- `packages/headless/tests/__snapshots__/*`: the `@sqlos/headless` public surface snapshot.

Adding an approved file is new coverage. It needs no entry, but it needs a baseline recorded from the released package (see the behavior-lock README), and an entry only when that baseline differs. Modifying or deleting one needs an entry. Renaming one without changing its content needs no entry. Renaming a scenario changes the first lines of its transcript, so it needs an entry naming the new path, and a line in `Baseline/renames.txt` that leads its baseline to it.

## Rules

1. A pure refactor never changes an approved file. If a refactor changes one, it changed behavior: fix the refactor, or justify the change here.
2. Every entry has one category:
   - **defect fixed**: the old behavior was wrong (a security gap, a spec violation, a crash, data loss, or a documented contract the code did not keep).
   - **DX improvement**: the old behavior worked but was harder to integrate, configure, operate, or diagnose than it needs to be.
   - **maintainability improvement**: an observable detail that only existed because of internal structure, such as the order of an unordered list, an error message wording, or a generated name.
3. Every entry links the issue that tracks the change, so the release notes and the migration guide can find it.
4. An entry lists every approved file it justifies by its repository-relative path in backticks. One entry may cover several files.
5. Entries are append-only. Never reuse or renumber an ID. To revise a decision, add a new entry that references the old one.
6. `scripts/check-behavior-ledger.sh` enforces rules 2 to 5 on every pull request. It fails when an approved file is modified, deleted, or renamed with changes without being named on a line the pull request adds to this ledger, and when an entry is missing a field.
7. `scripts/check-behavior-baseline.sh` holds the whole ledger to the baseline on every pull request. It fails when an approved file differs from its baseline (or is gone) and no entry names it, when an entry names a file that matches its baseline, and when a baseline file changes.
8. The baseline job runs every scenario against the released 7.2.1 package and compares it with the baseline, skipping nothing. The baseline shows what 7.2.1 does, the approved files what 8.0 does, and this ledger why they differ.

## Entry format

    ### BL-0001: One-line summary of the behavior change

    - **Approved files:** `tests/SqlOS.BehaviorLock/Scenarios/Example/Approved/ExampleScenarios.Example_scenario.verified.txt`
    - **Category:** defect fixed
    - **Justification:** What changes, for whom, why the old behavior was wrong or worse, and why no host needs to change code (or what it must change).
    - **Issue:** #NNN

Headings are `### BL-` followed by a four-digit number and a colon. The four fields are required, one per line, in any order. Add entries under **Entries** in ID order.

## Entries

### BL-0001: Timestamps read back from the database carry their UTC marker

- **Category:** defect fixed
- **Issue:** #325
- **Justification:** SqlOS stores every timestamp as UTC, but 7.2.1 read `datetime2` (SQL Server) and `timestamp without time zone` (PostgreSQL) back through EF with `DateTimeKind.Unspecified`, so JSON wrote those values without a `Z` and the dashboard, headless UIs and SCIM clients read UTC as local time (a 15-minute device code appeared to expire hours later). A value converter on every `DateTime` and `DateTime?` of every SqlOS entity now marks values read from the database as UTC; stored values are unchanged, host entities are untouched, and server-side expiry checks are unaffected because they compare instants. The transcripts change only in their timestamp format class, `{datetime:unspecified}` to `{datetime:utc-z}` (and the same for URL-encoded values); the EF model approvals show the converter on each timestamp property. The seven scenarios that locked the defect (`..._CurrentBehavior_KnownDefect_325`) are renamed to name the fixed behavior, and their captions and notes describe it; the baseline's rename log leads each one's 7.2.1 baseline to its new path. As a side effect the audit CSV export, which converted read-back times as local time, reports the true instant on hosts outside UTC. Hosts change no code; a host that compensated for the missing `Z` in its own UI can drop the workaround.

### BL-0002: Temporary tokens are issued and spent only through SqlOS

- **Category:** maintainability improvement
- **Issue:** #436
- **Justification:** `SqlOSTemporaryToken` keeps every public getter with its 7.2.1 name and type, so host queries (`db.Set<SqlOSTemporaryToken>()`, as the example integration tests write them) compile and read the same rows. Its public parameterless constructor and its setters become private: a token is issued, read and spent only through its typed kind (`SqlOSTemporaryTokenKinds`, docs/architecture/domain-model.md §15), which owns its purpose, payload format, lifetime and bindings, and the entity enforces the rules every token shares (only the SHA-256 hash of the raw token is stored, a single-use token is spent once and never after it expires, a payload is read and rewritten only as its own kind). A host that constructed a token or set its columns could bypass all of that. Hosts mint and spend tokens of their own purposes exactly as before through `SqlOSCryptoService.CreateTemporaryTokenAsync`, `FindTemporaryTokenAsync`, `ConsumeTemporaryTokenAsync` and `DeserializePayload`, whose signatures and behavior are unchanged (the example's OIDC hand-off does). Upgrade note: replace `new SqlOSTemporaryToken { ... }` and writes to its properties with those `SqlOSCryptoService` calls. Stored tokens, payload JSON, purposes and lifetimes are unchanged, and no transcript changes; only the public API approval shows the setters and the constructor gone.

### BL-0003: Email and phone code challenges change only through SqlOS

- **Category:** maintainability improvement
- **Issue:** #436

### BL-0004: Concurrent wrong email codes spend every attempt and close the challenge

- **Category:** defect fixed
- **Issue:** #424
- **Justification:** 7.2.1 compared an email code, then saved `AttemptCount + 1` from the count the request had loaded, with no lock or condition. Wrong codes sent together all loaded the same count and each wrote it plus one, so ten parallel guesses counted as one, the five-attempt limit never tripped, and an attacker could keep guessing a challenge sent to someone else's mailbox. Verification now spends the attempt first, with one conditional update (`AttemptCount < MaxAttempts`, still open and unexpired) that commits on its own, and compares the code only when that update spent one; the wrong code that spent the last attempt closes the challenge with a second conditional update (`max_attempts`), exactly once. These are the semantics of the 7.2.2 fix (PR #460), so carrying it forward reconciles trivially. Sign-in verification refuses to run inside a database transaction, whose rollback would erase the attempt; sign-up verification still runs inside the sign-up transaction until the 7.2.2 change that moves it out (#449) is carried forward. In the hosted scenario, ten parallel wrong codes now spend the five attempts and close the challenge: five failures are audited (one `max_attempts`, four `wrong_code`) where 7.2.1 audited ten `wrong_code` failures, the other five guesses are refused without an attempt or an audit row, and the right code is refused afterwards instead of signing in. Because which counted failure spent the last attempt depends on thread timing, that step's audit is recorded in content order (7.2.1's ten identical rows keep their write order in the package run), and the race barrier now also recognizes SQL Server's set-based `UPDATE [c] SET ... FROM [dbo].[...]`, so it holds every request at its attempt reservation on both providers. The public scenario shows the same: six parallel wrong guesses audit five failures (one `max_attempts`) instead of six, and the right code is refused. A right code now spends an attempt too, so a challenge answered on its last attempt stores `AttemptCount` equal to `MaxAttempts`; nothing reads the count but the limit. Both scenarios are renamed from `..._CurrentBehavior_KnownDefect_424` to the fixed behavior, and the baseline's rename log leads each one's 7.2.1 baseline to its new path. Hosts change no code.

### BL-0005: Email codes and sign-in links sent together never exceed their limits

- **Category:** defect fixed
- **Issue:** #424
- **Justification:** 7.2.1 enforced the email-code and sign-in-link send limits (per address, per IP address and per client) by counting recent challenges or links and then inserting its own, with nothing making the two atomic, so requests sent together all counted before any inserted and all were admitted: seven parallel requests sent seven codes or links to one address against a limit of five an hour. Both sends now go through the delivery admission password-reset emails and phone codes already use (`SqlOSDeliveryAdmissionService`, reached through the one internal admission gate): one atomic reservation of every applicable bucket in `SqlOSRateLimitBuckets`, made before anything is written and kept through delivery failures, so no interleaving admits more sends than a limit allows. The limits, their options and the refusal (`Too many sign-in code requests. Try again later.`, `Too many sign-in link requests. Try again later.`, and the `*.rate_limit_rejected` audit row naming `email`, `ip` or `client` in the 7.x order) are unchanged; a limit of zero still admits nothing, and a resend the cooldown refuses gives its reservation back, as it counted nothing in 7.2.1. As for password resets and phone codes, a limit now runs in fixed windows that start at a bucket's first send (and a reached limit stays reached until its window ends), where 7.2.1 counted the sends of the trailing hour or window, and sends made before an upgrade do not count against the new buckets. In the hosted scenarios, seven requests sent together now admit only what the hour still allows (four codes after the code that verified the address in setup, five links), which reach their insert and send, and refuse the rest before writing anything; the scenarios post the shown request first, so it is one of the admitted, and report the other tabs' answers in ascending order. In the public scenarios, six parallel requests now admit five and refuse one, observed after the admitted ones, and the parallel step's audit shows five starts (and five queued emails) and one `rate_limit_rejected` row. All four scenarios are renamed from `..._CurrentBehavior_KnownDefect_424` to the fixed behavior, and the baseline's rename log leads each one's 7.2.1 baseline to its new path. Hosts change no code.

### BL-0006: A password reset refuses a blank password on every surface

- **Category:** defect fixed
- **Issue:** #417
- **Justification:** 7.2.1 applied its only password rule (not blank, `Password is required.`) at sign-up, and nowhere else: a reset with an empty new password through the hosted page (`POST /sqlos/auth/password/reset/submit` with matching empty fields), the headless API (`POST /sqlos/auth/headless/password/reset`) or the JSON route (`POST /sqlos/auth/password/reset`) stored the hash of the empty string and spent the link, after which the account signed in with an empty password and the password its owner meant to set was refused. A reset now asks the password policy (`PasswordPolicy`, whose 8.0 rule is still 7.2.1's) before it looks at the link, so a refused password leaves the link usable (and a blank password with an unknown link is answered `Password is required.` without a `password_reset.invalid_or_expired` row). The hosted page answers `400` with `Password is required.` and keeps the token in its form; the headless API answers `400` with the same message; the JSON route throws, as it does for every refused reset (an unhandled `500`, #456). Sign-up on every surface already asked the policy, and BL-0007 makes `SqlOSUser.SetPassword`, which enforces it, the only way a password is stored. An operator-created user whose password is blank still has no password, as `AdminIdentityUserScenarios` records. The three new scenarios lock the fixed behavior, and their 7.2.1 baselines record the defect. #417 adds length, blocklist and breach-check rules through the same policy in 8.1. Hosts change no code.
