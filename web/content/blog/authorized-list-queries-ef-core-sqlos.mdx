Most authorization bugs do not start with a dramatic exploit. They start with a list endpoint.

The detail endpoint has a check:

```csharp
if (!await CanEdit(subjectId, documentId))
    return Results.Forbid();
```

But the list endpoint quietly returns too much:

```csharp
var todos = await db.TodoItems
    .Where(x => x.OwnerSubjectId == subjectId)
    .OrderBy(x => x.CreatedAt)
    .ToListAsync();
```

That works until the product adds teams, shared workspaces, organization admins, contractors, or nested resources. Then `owner_id = @uid` turns into copied filters, special cases, and post-query trimming. The user should only see rows they can access, and pagination should still be done by the database.

SqlOS FGA is built for that exact list endpoint.

## Point checks are not enough

A point check answers one question:

> Can this user edit this one todo?

An authorized list answers a different question:

> Which todos can this user read, sorted and paged like any other query?

Those are not interchangeable. If you load 500 rows and then call a permission service 500 times, you have already over-fetched data and broken pagination. Page 1 might shrink to three visible rows. Page 2 might include records that should have been on page 1.

The authorization check has to run in the database, as part of reading the page.

## Why owner_id breaks

The Todo sample starts intentionally small, but even it models the problem better than `owner_id`.

The resource hierarchy is:

```text
root
  tenant::{subjectId}
    todo::{todoId}
```

The grant is on the tenant root:

```text
subject user_123
  has role tenant_owner
  on resource tenant::user_123
```

The role includes:

```text
TENANT_CREATE_TODO
TODO_READ
TODO_WRITE
```

Every child todo inherits access from the tenant resource. The sample could add shared projects or organization workspaces later without changing the list endpoint shape. The row points to a resource, and the resource tree explains who can see it.

## The Todo item describes its FGA resource

Every protected entity implements `ISqlOSResourceEntity`. The stored `ResourceId` remains the bridge between the row and its authorization check, while the other properties tell SqlOS how to maintain the backing FGA resource:

```csharp
using SqlOS.Fga.Interfaces;
using SqlOS.Todo.Api.Services;

public sealed class TodoItem : ISqlOSResourceEntity
{
    public Guid Id { get; set; }
    public string ResourceId { get; set; } = string.Empty;
    public string OwnerSubjectId { get; set; } = string.Empty;
    public string Title { get; set; } = string.Empty;
    public bool IsCompleted { get; set; }
    public DateTime CreatedAt { get; set; }
    public DateTime? CompletedAt { get; set; }

    public string ResourceTypeId => TodoFgaService.TodoResourceTypeId;
    public string ResourceName => Title;
    public string? ParentResourceId => TodoFgaService.GetTenantResourceId(OwnerSubjectId);
    public string? ResourceDescription => null;
    public bool ResourceIsActive => true;
}
```

The todo row can still have app-specific columns, indexes, and constraints. SqlOS uses `ResourceId` to check the rows of a page and uses the entity-backed resource contract to sync the FGA resource row during `SaveChangesAsync`.

## The DbContext maps the SQL function

The Todo sample context derives from `SqlOSDbContext<TContext>`, which registers the SqlOS EF model and TVF mapping and keeps a copy of every index of a protected table under every node of the resource tree, current on save:

```csharp
public sealed class TodoSampleDbContext(DbContextOptions<TodoSampleDbContext> options)
    : SqlOSDbContext<TodoSampleDbContext>(options)
{
    public DbSet<TodoItem> TodoItems => Set<TodoItem>();

    protected override void OnApplicationModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<TodoItem>(entity =>
        {
            entity.HasKey(x => x.Id);
            entity.Property(x => x.ResourceId).HasMaxLength(450).IsRequired();
            entity.HasIndex(x => x.ResourceId).IsUnique();
            // The list pages newest first; SqlOS keeps this index under every node of the resource tree.
            entity.HasIndex(x => new { x.CreatedAt, x.Id });
        });
    }
}
```

SqlOS creates the backing SQL Server function during host startup, and `ToPageAsync` calls it to check the rows of a page. The `(CreatedAt, Id)` index adds a table for the newest-first order to the EF model, so the next migration creates it. A sort with no index still returns the right rows, but reads the table to fill a page, for every user.

## Before and after

The fragile version asks the app table to carry all authorization meaning:

```csharp
var items = await dbContext.TodoItems
    .AsNoTracking()
    .Where(x => x.OwnerSubjectId == currentSubjectId)
    .OrderByDescending(x => x.CreatedAt)
    .ToListAsync();
```

That is okay only while each todo has one owner and no sharing. The SqlOS version pages the same query for a subject and a permission:

```csharp
var page = await dbContext.TodoItems
    .AsNoTracking()
    .OrderByDescending(x => x.CreatedAt)
    .ToPageAsync(
        subjectId,
        TodoFgaService.TodoReadPermission,
        pageSize: 20,
        cursor,
        cancellationToken);

return Results.Ok(page.ToResponse(x => new
{
    x.Id,
    x.ResourceId,
    x.Title,
    x.IsCompleted,
    x.CreatedAt,
    x.CompletedAt
}));
```

`ToPageAsync` takes the `Where`, `OrderBy`, includes, and tracking you already write; project the page afterwards with `ToResponse`. It does not load unauthorized rows into memory first. The response is `{ data, pageSize, nextCursor, hasNextPage }`, and the client passes `nextCursor` back as `cursor` for the next page.

The page is the only way to read an authorized list. SqlOS has no authorized count and no unpaged list, because both cost every row the caller can see.

## Creating rows and resources together

When a todo is created, the app creates the domain row with a stable `ResourceId`. `SqlOSDbContext<TContext>` creates the backing FGA resource in the same `SaveChangesAsync` call:

```csharp
var todoId = Guid.NewGuid();
var item = new TodoItem
{
    Id = todoId,
    ResourceId = TodoFgaService.GetTodoResourceId(todoId),
    OwnerSubjectId = todoContext.SubjectId,
    Title = request.Title.Trim(),
    CreatedAt = DateTime.UtcNow
};

dbContext.TodoItems.Add(item);
await dbContext.SaveChangesAsync(cancellationToken);
```

The tenant root is the one resource in this sample that is not backed by a domain entity, so the service provisions it explicitly and keeps grants explicit:

```csharp
await _context.ProvisionResourceWithIdAsync(
    tenantResourceId,
    TodoFgaService.TenantResourceTypeId,
    displayName,
    "root",
    $"Todo tenant for {subjectId}",
    isActive: true,
    cancellationToken);

await _context.GrantRoleAsync(
    subjectId,
    tenantResourceId,
    TodoFgaService.TenantOwnerRole,
    cancellationToken);
```

That is the practical advantage of keeping app data and authorization data in the same database. If the business write fails, the resource write fails with it. If the resource cannot be created, the todo is not silently created with no authorization node.

## Mutations use point checks

List endpoints use pages. Mutations still use explicit checks against one resource:

```csharp
var access = await fgaAuthService.CheckAccessAsync(
    todoContext.SubjectId,
    TodoFgaService.TodoWritePermission,
    item.ResourceId);

if (!access.Allowed)
{
    return Results.Json(
        new { error = "Permission denied" },
        statusCode: 403);
}

item.IsCompleted = !item.IsCompleted;
await dbContext.SaveChangesAsync(cancellationToken);
```

The model is the same either way: subjects, resources, roles, permissions, grants. The list endpoint and the mutation endpoint do not invent separate authorization systems.

## What this solves

SqlOS FGA is not just a more expressive `CanEdit` helper. It solves the list problem:

- list only authorized rows
- keep the authorization check in SQL Server, with the page
- combine auth with search, sorting, and pagination
- support inherited access through a resource tree
- avoid per-row HTTP checks
- keep resource writes in the same transaction as business writes

If you are evaluating Auth0 FGA or WorkOS FGA, the next posts compare the architecture tradeoffs. This post is the SqlOS problem statement: your .NET app needs authorized list queries, and those list queries already live in EF Core.
