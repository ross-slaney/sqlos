You'll learn how to run the full test suite and focused filters while developing auth or FGA features.

![SqlOS local and CI testing pipeline](/docs/guides-testing.svg)

## Test layout

- `tests/SqlOS.Tests` — unit tests
- `tests/SqlOS.IntegrationTests` — real SQL Server or PostgreSQL (Aspire container; set `SQLOS_TEST_PROVIDER=postgresql` for Postgres, or `SQLOS_TEST_SQLSERVER_RCSI=1` to run SQL Server with read-committed snapshot, the Azure SQL default)
- `examples/SqlOS.Example.IntegrationTests` — example API flows
- `examples/SqlOS.Todo.IntegrationTests` — Todo sample flows
- `tests/SqlOS.Benchmarks` — authorization benchmarks on SQL Server and PostgreSQL, 1M to 50M products in CI

## Run everything

```bash
dotnet build SqlOS.sln
./scripts/unit-tests.sh
./scripts/integration-tests.sh
./scripts/docs-check.sh
```

`docs-check.sh` runs the website lint, production build, and link validation across repo and site docs.

## Integration coverage

Integration tests use Aspire and SQL Server or PostgreSQL containers for:

- Auth and FGA schema bootstrap
- OAuth, OTP, and invitation flows
- AuthServer resilience across app instance replacement, including shared signing-key custody and full PKCE token exchange
- signing-key fail-closed behavior for a lost ring, plaintext rows, database-only compromise, concurrent rotation, JWKS grace, and cleanup
- Client registration and resource indicators
- FGA checks and EF query composition
- Example and Todo sample end-to-end paths

Authorization checks and list filters run in the database. Unit tests on an in-memory provider can check the grants a feature creates, but not the access decision; test that against SQL Server or PostgreSQL.

## Focused runs

```bash
dotnet test tests/SqlOS.Tests/SqlOS.Tests.csproj --filter SqlOSInvitationServiceTests
dotnet test tests/SqlOS.Tests/SqlOS.Tests.csproj --filter RequestEmailOtpSignupAsync
dotnet test tests/SqlOS.IntegrationTests/SqlOS.IntegrationTests.csproj --filter AuthServerSigningKeyResilienceIntegrationTests
```

Coverage settings live in `tests/coverlet.runsettings`.

## Benchmarks

`tests/SqlOS.Benchmarks` measures list filtering and point checks on the schema, the resources table's closure with its per-level indexes, the functions, and the lineage triggers that SqlOS ships. Every page is the LINQ query an application writes with the filter `BuildFilterAsync` returns, and the filter it picked for the caller (list first or check each row) is reported with the timing. The catalog grows in place from 100K to 1M products on every CI run and to 50M on a labelled pull request, every answer is checked against ground truth, each page's actual plan is captured, and the lineage is checked against SqlOS's own rebuild after a maintenance pass of inserts, deletes, and subtree updates.

```bash
# PostgreSQL, 100K and 1M products; the harness starts the database with Testcontainers
dotnet run --project tests/SqlOS.Benchmarks -c Release -- --provider postgresql

# SQL Server at the CI scales, with database files on a large disk
dotnet run --project tests/SqlOS.Benchmarks -c Release -- --provider sqlserver --scales 1m,10m,50m --data-dir /mnt/sqlos-bench
```

The `Benchmarks` workflow runs one job per engine beside pull-request CI whenever `src/SqlOS` changes. It fails on a wrong answer, on a lineage that differs from the rebuild, on per-page cost that grows with the catalog, on either filter form being slower than the previous release's, on the sparse pages not beating it by the configured ratios, or on a median above its budget in `tests/SqlOS.Benchmarks/gates.json`. The project README explains the dataset, the scenarios, and how to read the results.

## Test control-plane parity

Administrative capabilities that support code-first configuration, programmable administration, and the dashboard use `ControlPlaneParityHarness` in `tests/SqlOS.Tests/Infrastructure`. The harness starts a production endpoint map on ASP.NET Core TestServer and provides three deliberate entry paths:

1. configure strongly typed startup seeds and run the real reconcilers;
2. call the public administration service directly;
3. send the exact JSON payload to the admin route used by the embedded dashboard.

Add a focused parity case rather than copying a complete host fixture. Load a canonical projection containing stable, non-secret configuration; compare semantic values; and assert expected ownership differences (`code` versus `dashboard`) separately. Then invoke a runtime behavior such as OAuth authorization-request validation, provider discovery, SCIM bearer authentication, or effective policy resolution.

The representative suite covers OAuth clients, machine clients, upstream OIDC connections, inbound SCIM connections, and global MFA settings. It also checks invalid-input semantics, one-time secret reveal versus redacted reads, audit outcomes, dashboard JavaScript route/field drift, parallel isolation, and real SQL persistence across DbContext instances.

When adding a new administrative capability, use this checklist:

- use production seeds, services, routes, request contracts, and runtime services;
- normalize random IDs and timestamps rather than snapshotting them;
- never place raw secrets, encrypted values, bearer tokens, or hashes in projections or failure output;
- prove code-owned records are observable but not editable, while dashboard-owned records remain editable;
- assert disable/re-enable and reconciliation behavior where the capability has a lifecycle;
- add real SQL coverage when locking, uniqueness, persistence, or concurrent reconciliation matters;
- document an inapplicable control plane instead of adding an artificial UI for an internal secure default.

Run the focused suite with:

```bash
dotnet test tests/SqlOS.Tests/SqlOS.Tests.csproj --filter SqlOSControlPlaneParityTests
dotnet test tests/SqlOS.IntegrationTests/SqlOS.IntegrationTests.csproj --filter ControlPlaneParityPersistenceIntegrationTests
```
