>
  `BuildFilterAsync` is the whole API. Compose its filter into any query: a page, a count, a join. It asks the database whether the caller sees few rows or many, and returns the filter that fits: list the caller's rows first, or check each row in the page's order.
</Banner>

## A page

```csharp
var canView = await fga.BuildFilterAsync<InventoryItem>(
    subjectId, RetailPermissionKeys.InventoryView);

var rows = await db.InventoryItems
    .AsNoTracking()
    .Where(canView)
    .Where(i => i.LocationId == locationId)
    .OrderBy(i => i.Name).ThenBy(i => i.Id)
    .Take(pageSize + 1)
    .ToListAsync();

var hasNextPage = rows.Count > pageSize;
if (hasNextPage) rows.RemoveAt(pageSize);
```

That is an ordinary EF Core query, and it runs as one. The filter in it is one `EXISTS`, and `BuildFilterAsync` picked which one by asking the database how many rows this caller sees, counted up to a cap that grows with the square root of the table. For a caller below the cap, the rows are listed first: the database works out the caller's resources from their grants, finds those rows through your table's `ResourceId` index, sorts them and takes the page. For a caller at or above the cap, the database reads your table in the page's order and checks each row until the page is full. [List filtering](/docs/fga/list-filter#how-a-page-runs) describes both and what each costs.

Nothing about the query is special. Any order, in any direction or mix of directions; any condition, including one through a navigation; a `Select` before or after the order; `Skip`; `First` or `Single`; `Count`, `Any`, `GroupBy`; `ExecuteUpdate` and `ExecuteDelete`: all of them compose. There is no query shape SqlOS recognizes and none it declines. `BuildFilterAsync` itself resolves the caller's principals and the permission and asks the database its one question; the statement reads the grants again when it runs.

### The cursor

The next page is a keyset predicate over the order, the one EF Core keyset pagination writes anyway:

```csharp
// lastName, lastId: the last row of the previous page, decoded from the cursor your endpoint issued
.Where(i => i.Name.CompareTo(lastName) > 0 || (i.Name == lastName && i.Id > lastId))
```

The database reads it as it reads any predicate: with an index on the order (`HasIndex(i => new { i.Name, i.Id })`), it seeks to the position and reads forward. A keyset written another way is still correct; it is just a predicate the index may not seek on.

Encode the last row's order values as an opaque cursor for the client to send back; `SqlOSCursorCodec` does that (the Todo sample's list endpoint shows it end to end). A fresh request uses current grants and seeks after the supplied key. It is not a retained snapshot: a newly visible row before the cursor will not appear unless the list is restarted, and concurrent sort-key changes can move rows across the boundary. Use the cursor to resume the current ordering, not as a change feed.

### What it costs

A page is one statement, once `BuildFilterAsync` has resolved the caller and asked its question: SqlOS keeps no candidate buffer and holds nothing between pages. For a table of N rows, of which the caller may see V, and a page of P rows:

- A caller who sees few rows (one store, one workspace) has them listed first: about V index reads, the rows beneath their grants, and a sort. It does not grow with the table.
- A caller who sees most rows (an administrator) has each row checked in the page's order: about P rows. It does not grow with the table.
- Between the two, the caller's rows are listed first below the cap and checked at or above it. The worst page is near the cap, where the two cost about the same, and it grows with the square root of the table, not with the table.
- A caller with k grants on single resources costs about k index reads inside the database while k is below the cap; above it, the rows are checked and the number of grants no longer matters.
- The question before the page reads at most the cap's worth of index entries.

One case reads more: a caller who sees many rows, all at the far end of the page's order (a long-dormant customer's rows, newest first), has every row before them read and checked. [List filtering](/docs/fga/list-filter#what-determines-query-cost) explains why, and what helps when the screen is scoped to that customer.

Declare an index for the order you page in, ended by the key, so checking each row seeks to the cursor and reads forward; without it, the database reads every row the filter passes and sorts them, which for a caller who sees many rows is the whole table. A condition the sort index cannot narrow is tested as rows arrive, so a page over a selective condition reads more rows than it returns; give the condition its own index, or lead a compound index with it, as you would for any query. A later page costs what the first page costs, and a caller who sees nothing has nothing to list; there is nothing to discover or merge before a page. The numbers are measured in `tests/SqlOS.Benchmarks`.

[Designing your resource tree](/docs/fga/designing-your-resource-tree) explains why workspace grants, groups and stable hierarchy boundaries keep V small for the callers who should see little.

## The filter, for everything else

Anything you compose after `.Where(filter)` that is not a page (projections with joins, aggregates, offset pagination over a projection, a list without `Take`) ends up in the same kind of statement, with the authorization predicate in it. It is the tool for counts, dashboards and joins.

### Offset pagination over a projection

```csharp
var canView = await fga.BuildFilterAsync<InventoryItem>(
    subjectId, RetailPermissionKeys.InventoryView);

var items = await db.InventoryItems
    .Where(canView)
    .Where(i => i.LocationId == locationId)
    .Select(i => new InventoryItemDto
    {
        Id = i.Id,
        Name = i.Name,
        LocationName = i.Location!.Name
    })
    .OrderBy(d => d.Name).ThenBy(d => d.Id)
    .Skip(page * pageSize).Take(pageSize)
    .ToListAsync();
```

One statement, the projection's join planned beside the filter; fine for small admin-style lists. A large `Skip` reads the skipped rows, so for large tables or infinite scrolling use a keyset cursor, as above.

### Keyset pagination with an external package

Keyset (cursor/seek) pagination works with any library that composes on `IQueryable`, such as [MR.EntityFrameworkCore.KeysetPagination](https://github.com/mrahhal/MR.EntityFrameworkCore.KeysetPagination). The package's predicate is a `Where` over the entity's columns like any other, and the filter composes beside it.

### What the filter costs

A count, a join or a list without `Take` reads every row the caller may see. For a caller whose rows are listed first, that is their rows. For a caller who sees many rows, it is the whole table with each row checked, as a count of the table reads the table. The filter adds one point check per row read, or one index read per visible row, and never reads the grant list into the application.

### What the filter captures

The *principal set* (the subject plus its group memberships) and the permission are resolved when `BuildFilterAsync` is awaited, and the database answers its question then, which picks the filter. Every statement reads the caller's grants again when it runs, so a query sees the grants of its moment, and the caller's own lifecycle is rechecked by each query too; a grant that changed since can make the chosen filter slower or faster, never wrong. Build the filter once per request, so each request's queries see the principal set current at that request; do not cache it in statics or reuse it across requests. The filter holds no context: compose it on any instance of the context registered with `AddSqlOS`, from a factory or a pool included.

## Always end with a unique tiebreaker

Whatever pagination style you use, always end the `OrderBy` chain with a unique column (typically `Id`):

```csharp
.OrderBy(d => d.Name).ThenBy(d => d.Id)
```

Without a unique tiebreaker, rows that share the same sort value have no deterministic order, so rows can be skipped or duplicated across pages. SqlOS does not add one for you.

## Admin surfaces

SqlOS's own dashboard and admin APIs use an internal keyset helper with opaque versioned cursors — see [Admin cursor pagination](/docs/guides/admin-cursor-pagination). That contract is for SqlOS admin endpoints; application lists compose `BuildFilterAsync` as above.
