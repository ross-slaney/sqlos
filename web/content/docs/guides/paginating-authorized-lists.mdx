>
  Page your query with ToPageAsync, sorted however the screen sorts. A page reads at most a small multiple of the rows the caller can see, and never much more than the old scan; declaring a hot sort with HasPageOrder makes it about a page for every caller.
</Banner>

`ToPageAsync` is how SqlOS reads an authorized list, and the only way. One resource is a point check, [`CheckAccessAsync`](/docs/fga/checking-a-permission). There is no authorized count, `Any`, join, or unpaged list: each of those costs every row the caller can see. Page instead.

## Page

```csharp
protected override void OnApplicationModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Product>(entity =>
    {
        entity.HasKey(p => p.Id);
        entity.HasIndex(p => p.ResourceId).IsUnique();
        entity.HasIndex(p => new { p.Price, p.Id });   // your index for the order
    });
}
```

```csharp
var page = await db.Products
    .AsNoTracking()
    .Include(p => p.Location)                 // optional
    .Where(p => p.Name.Contains(term))        // optional, any number
    .OrderBy(p => p.Price)                    // required: the order (ThenBy allowed)
    .ToPageAsync(subjectId, "product.view", pageSize: 20, cursor: request.Cursor, cancellationToken);

return Results.Ok(page.ToResponse(p => new ProductDto(p)));
```

Nothing is declared for the order: every order pages. Because `Product` implements `IHasResourceId`, SqlOS adds its node index to your EF model, `SqlOSFgaPage_Products_Id` in SqlOS's schema: which rows sit under which node of the resource tree. Your next migration creates it, and SqlOS keeps it current. Nothing is added to your own tables. Index the order on your own table (`HasIndex(p => new { p.Price, p.Id })`): callers who see most of the table page from it.

`subjectId` is the caller; its active group memberships are included. `"product.view"` is the permission each row's resource must grant. Both are resolved each time the page runs.

`ToPageAsync` returns `SqlOSCursorPage<T>`: `Data`, `PageSize`, `NextCursor`, and `HasNextPage`. `ToResponse(selector)` shapes it as `{ data, pageSize, nextCursor, hasNextPage }`. `NextCursor` is `null` on the last page; a page that ends exactly at the last row may be followed by an empty one.

Project after the page (`page.ToResponse(...)` or `page.Data.Select(...)`), not before it.

### How a page runs

SqlOS resolves the caller's subjects and the permission, then reads in rounds. The budget `b` starts at the page size and grows four times per round.

1. **Your query, checked.** The next `b` rows of your query, in its order, each checked with SqlOS's authorization function. If a page of them is visible, or your query has no more rows, that is the page. A caller who sees most rows gets the page here, in the first round, and nothing else runs.
2. **The caller's rows, sorted.** In the same round, up to `b + 1` of the caller's row keys from the node index, under each resource the caller is granted (the minimal set: a grant under another grant adds nothing). If there are at most `b`, they are all of the caller's rows: SqlOS reads those rows through your query, with your filters, the cursor and the order, and the first page of them is the page. A caller who sees few rows gets the page here.
3. **A declared order instead.** For an order declared with [`HasPageOrder`](/docs/guides/optimizing-page-orders), step 2 reads the order under each of the caller's nodes and merges them, applying your filters before the per-node limit: about a page for any caller, in the first round.
4. **The page.** The page's rows are loaded through your query, so `Include`, tracking and your filters apply, and checked once more. The final check can drop a stale row, never add one.

Each step is an EF Core query, logged like any other. One Debug line per page under the `SqlOS.Fga` category records the order and whether it is declared, the rounds, the rows each read touched, which read produced the page, and the rows the final check dropped:

```text
ToPageAsync Product by Price, Id asc (page order not declared): 3 round(s); read 1 rows per round [20, 80, 320]; read 2 entries per node per round []; read 3 keys per round [21, 81, 244]; page from read 3; 0 row(s) dropped by the final check; 64 ms.
```

## The cursor

The cursor is opaque. It carries the last row's order values, bound to the entity, the order and its direction, and you pass it back as it came. Consecutive pages can come from different steps; the cursor continues either way.

**Don't write your own position filter.** No `.Where(x => x.CreatedAt < lastSeen)`, no keyset library, no `since=` version parameter: pass `NextCursor` back. `ToPageAsync` reads from the cursor in every step. A hand-written position is just another filter there, so every page reads the caller's rows from the start of the order.

For a change feed, the cursor is the sync token the client stores. Keep the last `NextCursor` you received. `NextCursor` is `null` on the last page, so the next read from the stored cursor returns that last page again, followed by anything newer.

- A cursor that is not one this list issued (edited, truncated, or not a cursor) throws `SqlOSCursorException`. Map it to `400` with `SqlOSCursorPagination.BadRequest(exception)` or your own response.
- A cursor issued for another list (another entity, order, or direction) throws `ArgumentException` with `ParamName` `"cursor"`. A client that changes the sort and keeps the cursor gets this; map it to `400` too.

```csharp
try
{
    page = await query.OrderBy(i => i.Price).ToPageAsync(subjectId, "product.view", pageSize, cursor, ct);
}
catch (Exception exception) when (exception is SqlOSCursorException or ArgumentException { ParamName: "cursor" })
{
    return Results.BadRequest(new { error = SqlOSCursorException.ErrorCode, message = exception.Message });
}
```

## What the query may contain

Before `ToPageAsync`: `Where`, `Include`/`ThenInclude`, `AsNoTracking`/`AsTracking`, `TagWith`, `IgnoreQueryFilters`, `AsSplitQuery`, and one `OrderBy`/`OrderByDescending` with any number of `ThenBy`/`ThenByDescending` in the same direction, each over a mapped scalar property. The ordering comes last.

`ToPageAsync` throws `ArgumentException` for a query that does not start from a `DbSet` of a context deriving from `SqlOSDbContext<TContext>`; no `OrderBy`; mixed directions; an order over anything but a mapped, non-nullable scalar property; and `Select`, `Skip`, `Take`, `Distinct`, `GroupBy`, `Join`, `SelectMany`, `Union` or `Concat` in the chain. `pageSize` is 1 to 1,000.

For an unknown or inactive subject, or an unknown permission, `ToPageAsync` logs a warning and returns an empty page with no `NextCursor`, without running the page's queries.

## What a page costs

Call `R1` the rows of your query that step 1 needs, from the cursor up to the page's last visible row (or all of them), and `V` the rows the caller can see. The rounds stop at the first budget that holds either, so a page with no declared order reads at most about nine times the smaller of the two, plus a page:

- **A caller who sees most rows:** about a page, from step 1 alone, with the same statements as a declared order.
- **A caller who sees few rows:** about its own rows plus a page, from step 2.
- **A caller whose rows are spread through the order:** the smaller of the two is at most about √(rows × page size), the worst case: 4,472 for a million rows and a page of 20.
- **A caller whose rows bunch at the far end of the order:** about its own rows. Step 1 finds nothing until the end, so step 2 settles the page once the budget holds them.

A declared order makes every one of these about a page. [Optimizing page performance](/docs/guides/optimizing-page-orders) has the benchmark at a million rows, and when a declaration is worth its storage and writes.

- **Many grants:** step 2 resolves the caller's minimal granted nodes in each round it runs, so a caller with ten thousand single-row grants pays that resolution once per round. See [Designing your resource tree](/docs/fga/designing-your-resource-tree).
- **Your filters** apply after the node index in step 2: an application filter that few of the caller's rows pass still costs the caller's rows, never the table.
- **On PostgreSQL**, when the caller's rows are a percent or more of the table, the planner can read them in step 2 with one parallel sequential scan instead of looking each one up, because it estimates that cheaper. The page then reads the table once, without checking each row. Step 1 checks each row with SqlOS's authorization function inlined into the query, so at large budgets its estimated cost crosses PostgreSQL's JIT thresholds and compilation adds to it. [Optimizing page performance](/docs/guides/optimizing-page-orders#on-postgresql) has the numbers.

## Keeping page orders current

SqlOS keeps two kinds of page-order tables, both in SqlOS's schema and both in your EF model: the node index of every entity that implements `IHasResourceId`, and one table per order declared with `HasPageOrder`. An entity that cannot have them (an owned type, a view, TPT or TPC inheritance, a composite or missing primary key, or no mapped `ResourceId`) gets none: startup logs one warning per entity naming the reason, and its pages run step 1 only.

`SqlOSDbContext<TContext>` keeps every one of them current in the same transaction as each save: rows inserted, deleted, or updated in an order column or `ResourceId`, and resources added, moved, deactivated, reactivated or deleted, whether through your entities, `ISqlOSResourceEntity`, the resource helpers in `SqlOS.Extensions`, the dashboard, or the seed service. It reads what the save wrote, so values set by `SaveChanges` interceptors and `SavingChanges` handlers, cascade deletes, and order columns the database computes are included. A save's entry statements go to the database as one command.

It uses your transaction when there is one, inside a savepoint so that a failed save leaves your transaction as it was before the save; an ambient or enlisted `System.Transactions` transaction; and otherwise its own, inside the context's execution strategy.

- **Index `ResourceId`** on protected tables (`HasIndex(p => p.ResourceId)`): a save that adds, moves or deletes a resource finds the rows under it by `ResourceId`.
- **Writes that bypass EF Core** (bulk loads, raw SQL, `ExecuteUpdate`/`ExecuteDelete`, triggers) do not update entries, and neither does an interceptor that changes protected rows during a save that changes no protected row or resource. Until you call `ISqlOSFgaAuthService.RebuildPageOrdersAsync()`, rows they insert are missing from pages served by steps 2 and 3, and rows they change page at their old position. A row the caller may not see is never returned: every page row is checked once more. The rebuild rewrites the node indexes and every declared order, one transaction per table, without a command timeout; the cost is the table's rows times the tree depth. Run it while the application is not writing to those tables: a save during a rebuild waits for it, or makes it fail with a deadlock or duplicate key, and running it again fixes that.
- **Upgrading, or a new declaration on a table that already has rows:** add the migration that creates the new tables. The first start after it fills each empty table from the rows already there and logs how many; it runs before the application serves requests and takes about as long as a rebuild. Until the migration runs, the table is missing: SqlOS logs a warning at startup, saves still succeed, and pages that would use the table run step 1 only. In a rolling deployment, instances still on the previous version write rows without entries: call `RebuildPageOrdersAsync()` once every instance runs the new version.
- **Concurrent hierarchy changes.** If one save moves, deactivates or reactivates a resource while another adds or changes rows under it, those rows can, rarely, be missing from pages until a rebuild (PostgreSQL, and SQL Server with `READ_COMMITTED_SNAPSHOT`), or one of the saves fails with a deadlock or duplicate key; retry it.
- **Schema tools.** Page-order tables are ordinary tables in your EF model. Because they are derived, a change that a tool blocks for possible data loss on one of them (a source column narrowed) is resolved by emptying the table and letting the next start refill it.
- **Hand-rolled contexts** (a `DbContext` that implements `ISqlOSFgaDbContext` itself) get no maintenance and no pages: `ToPageAsync` refuses their queries. Derive from `SqlOSDbContext<TContext>` to page.

## What it costs

- **Storage:** the node index holds one entry per row per level of its resource path: a product four levels under the root has five. Each declared order adds as many again, with the order's columns.
- **Writes:** with no declared order at all, every protected entity still pays its node index. Inserting a row, or changing its `ResourceId`, writes one entry per level of its resource path in the save's transaction, and a save of a protected row or a resource runs in a transaction. Adding, moving, deactivating or reactivating a resource rewrites the entries of the rows under it; for a new resource that is one `ResourceId` lookup per table. Each declared order writes as many entries again, also when one of its columns changes.
- **Reads:** at most about nine times the smaller of `R1` and `V` per page, plus a page (above); about a page for a declared order.

## Authorization is evaluated at query time

Each page checks grants when it runs. If grants change between pages, newly authorized rows appear and newly revoked rows disappear from the next page: the cursor is a position in the order, not a snapshot of the first page. A revoked subject stops seeing rows on the very next page.

The *principal set* (the subject plus its active group memberships) is resolved each time `ToPageAsync` runs, and each page's queries check the caller's activity again when they run. Membership and lifecycle changes apply from the next page.

## Admin surfaces

SqlOS's own dashboard and admin APIs use an internal keyset helper with opaque versioned cursors — see [Admin cursor pagination](/docs/guides/admin-cursor-pagination). That contract is for SqlOS admin endpoints; application lists page with `ToPageAsync`.
