  Declare the orders a list is paged by, then page your query with ToPageAsync. A page costs about a page of work for any caller: one who sees everything, one who sees three rows of a million, one with ten thousand grants.
</Banner>

## Declare the order

```csharp
protected override void OnApplicationModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Product>(entity =>
    {
        entity.HasKey(p => p.Id);
        entity.HasIndex(p => p.ResourceId).IsUnique();
        entity.HasIndex(p => new { p.Price, p.Id });             // your index for the order
        entity.HasPageOrder(p => p.Price);                       // (Price, Id)
        entity.HasPageOrder(p => new { p.Status, p.CreatedAt }); // (Status, CreatedAt, Id)
    });
}
```

- The primary key is appended when it is not already last, so `(Price)` means `(Price, Id)`. Declaring the same order twice is a no-op.
- One declaration serves ascending and descending pages. Every column of an order runs in one direction.
- Order columns are non-nullable mapped properties; strings need `HasMaxLength` (or an explicit column type). The entity needs a single-column primary key, a mapped `ResourceId`, and a table of its own: no owned types, views, or TPT/TPC inheritance (TPH is fine; declare the order on the root type). These rules are checked when the model is built, with the fix in the message.
- Each declaration adds a table to your EF model, `SqlOSFgaPage_{Table}_{Columns}` in SqlOS's schema, so your next migration (or a model-driven tool such as EFCore.SchemaSync) creates it. Nothing is added to your own tables.
- Index the order on your own table too (`HasIndex(p => new { p.Price, p.Id })`): callers who see most of the table page from it.

## Page

```csharp
var canView = await fga.BuildFilterAsync<Product>(subjectId, "product.view");

var page = await db.Products
    .AsNoTracking()
    .Include(p => p.Location)                 // optional
    .Where(p => p.Name.Contains(term))        // optional, any number
    .OrderBy(p => p.Price)                    // required: the order (ThenBy allowed)
    .ToPageAsync(canView, pageSize: 20, cursor: request.Cursor, cancellationToken);

return Results.Ok(page.ToResponse(p => new ProductDto(p)));
```

`ToPageAsync` returns `SqlOSCursorPage<T>`: `Data`, `PageSize`, `NextCursor`, and `HasNextPage`. `ToResponse(selector)` shapes it as `{ data, pageSize, nextCursor, hasNextPage }`. `NextCursor` is `null` on the last page; a page that ends exactly at the last row may be followed by an empty one.

Project after the page (`page.ToResponse(...)` or `page.Data.Select(...)`), not before it.

### How a page runs

1. **Your query, checked.** The next rows of your query, in its order, each checked like `.Where(filter)` checks it. For a caller who sees most rows, this fills the page.
2. **The caller's nodes, in order.** When few of those rows are visible and the order is declared, SqlOS reads the order under each resource the caller is granted (the minimal set: a grant under another grant adds nothing) and merges them, applying your filters before the per-node limit. For a caller who sees little, this fills the page.
3. **The page.** The page's rows are loaded through your query, so `Include`, tracking and your filters apply, and checked against the filter once more. The final check can drop a stale row, never add one.

Each step is an EF Core query, logged like any other. One Debug line per page under the `SqlOS.Fga` category records the rounds, the rows each step read, which step produced the page, and the rows the final check dropped.

## The cursor

The cursor is opaque. It carries the last row's order values, bound to the entity, the order and its direction, and you pass it back as it came. You no longer write keyset predicates: `ToPageAsync` applies the position to both reads.

- A cursor that is not one this list issued (edited, truncated, or not a cursor) throws `SqlOSCursorException`. Map it to `400` with `SqlOSCursorPagination.BadRequest(exception)` or your own response.
- A cursor issued for another list (another entity, order, or direction) throws `ArgumentException` with `ParamName` `"cursor"`. A client that changes the sort and keeps the cursor gets this; map it to `400` too.

```csharp
try
{
    page = await query.OrderBy(i => i.Price).ToPageAsync(canView, pageSize, cursor, ct);
}
catch (Exception exception) when (exception is SqlOSCursorException or ArgumentException { ParamName: "cursor" })
{
    return Results.BadRequest(new { error = SqlOSCursorException.ErrorCode, message = exception.Message });
}
```

## What the query may contain

Before `ToPageAsync`: `Where`, `Include`/`ThenInclude`, `AsNoTracking`/`AsTracking`, `TagWith`, `IgnoreQueryFilters`, `AsSplitQuery`, and one `OrderBy`/`OrderByDescending` with any number of `ThenBy`/`ThenByDescending` in the same direction, each over a mapped scalar property. The ordering comes last.

`ToPageAsync` throws `ArgumentException` for a filter that did not come from `BuildFilterAsync`; no `OrderBy`; mixed directions; an order over anything but a mapped, non-nullable scalar property; `Select`, `Skip`, `Take`, `Distinct`, `GroupBy`, `Join`, `SelectMany`, `Union` or `Concat` in the chain; a context that does not derive from `SqlOSDbContext<TContext>`; and a filter built on a different context instance than the query. `pageSize` is 1 to 1,000.

For an unknown subject or permission, `BuildFilterAsync` returns a filter that matches nothing, and `ToPageAsync` returns an empty page without querying.

## Orders that are not declared

A query ordered by an order that is not declared still returns the right pages. It runs step 1 only, reading your query in growing batches until a page is visible, which is the old `.Where(filter)` cost: a caller who sees little of a large table reads most of it. The first time a page needs more than one batch, SqlOS logs a warning naming the declaration to add:

```text
ToPageAsync scanned 1240 rows of Product ordered by CreatedAt, Id asc to fill a page of 20. No page order is declared for it, so pages for callers who can see few rows read the table. Declare modelBuilder.Entity<Product>().HasPageOrder(e => e.CreatedAt) and add a migration.
```

## Keeping page orders current

`SqlOSDbContext<TContext>` keeps every page order current in the same transaction as each save: rows inserted, deleted, or updated in an order column or `ResourceId`, and resources added, moved, deactivated, reactivated or deleted, whether through your entities, `ISqlOSResourceEntity`, the resource helpers in `SqlOS.Extensions`, the dashboard, or the seed service. It reads what the save wrote, so values set by `SaveChanges` interceptors and `SavingChanges` handlers, cascade deletes, and order columns the database computes are included. A save's entry statements go to the database as one command.

It uses your transaction when there is one, inside a savepoint so that a failed save leaves your transaction as it was before the save; an ambient or enlisted `System.Transactions` transaction; and otherwise its own, inside the context's execution strategy.

- **Index `ResourceId`** on paged tables (`HasIndex(p => p.ResourceId)`): a save that adds, moves or deletes a resource finds the rows under it by `ResourceId`.
- **Writes that bypass EF Core** (bulk loads, raw SQL, `ExecuteUpdate`/`ExecuteDelete`, triggers) do not update entries, and neither does an interceptor that changes paged rows during a save that changes no paged row or resource. Until you call `ISqlOSFgaAuthService.RebuildPageOrdersAsync()`, rows they insert are missing from pages and rows they change page at their old position. A row the caller may not see is never returned: every page row passes the filter once more. The rebuild rewrites every declared order, one transaction per order, without a command timeout; the cost is the table's rows times the tree depth. Run it while the application is not writing to those tables: a save during a rebuild waits for it, or makes it fail with a deadlock or duplicate key, and running it again fixes that.
- **A new declaration on a table that already has rows** is filled at startup: once the migration has created the empty entry table, the first start writes its entries and logs how many. The fill runs before the application serves requests and takes about as long as rebuilding that order. Until the migration runs, the entry table is missing; SqlOS logs a warning at startup and pages for that order run step 1 only. In a rolling deployment, instances still on the previous version write rows without entries: call `RebuildPageOrdersAsync()` once every instance runs the new version.
- **Concurrent hierarchy changes.** If one save moves, deactivates or reactivates a resource while another adds or changes rows under it, those rows can, rarely, be missing from pages until a rebuild (PostgreSQL, and SQL Server with `READ_COMMITTED_SNAPSHOT`), or one of the saves fails with a deadlock or duplicate key; retry it.
- **Schema tools.** Entry tables are ordinary tables in your EF model. Because they are derived, a change that a tool blocks for possible data loss on an entry table (a source column narrowed) is resolved by emptying the entry table and letting the next start refill it.
- **Hand-rolled contexts** (a `DbContext` that implements `ISqlOSFgaDbContext` itself) get no maintenance, and `ToPageAsync` refuses them. Derive from `SqlOSDbContext<TContext>` to page, or keep `.Where(filter)`.

## What it costs

- **Storage:** one entry per row per level of its resource path, per declared order. A product four levels under the root has five entries per order.
- **Writes:** inserting a row, or changing an order column or its `ResourceId`, writes that many entries in the save's transaction. Adding, moving, deactivating or reactivating a resource rewrites the entries of the rows under it; for a new resource that is one `ResourceId` lookup per declared order.
- **Reads:** about a page for every caller and every page position. The exception is an application filter that few rows pass combined with a caller whose rows barely overlap it: step 2 reads the caller's entries until a page passes your filter.

Grants on the nodes of your tree keep the caller's node set small; a caller with ten thousand single-row grants costs ten thousand seeks per page in step 2. See [Designing your resource tree](/docs/fga/designing-your-resource-tree).

## Authorization is evaluated at query time

Each page checks grants when it runs. If grants change between pages, newly authorized rows appear and newly revoked rows disappear from the next page: the cursor is a position in the order, not a snapshot of the first page. A revoked subject stops seeing rows on the very next page.

The *principal set* (the subject plus its group memberships) is captured when `BuildFilterAsync` is awaited. Build the filter once per request; do not cache it in statics or reuse it across requests.

## Admin surfaces

SqlOS's own dashboard and admin APIs use an internal keyset helper with opaque versioned cursors — see [Admin cursor pagination](/docs/guides/admin-cursor-pagination). That contract is for SqlOS admin endpoints; application lists page with `ToPageAsync`.
