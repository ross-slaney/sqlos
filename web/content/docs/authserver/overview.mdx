## Setup

```csharp
builder.Services.AddDataProtection()
    .SetApplicationName("Acme.Identity")
    .PersistKeysToFileSystem(new DirectoryInfo(signingKeyRingPath));

builder.AddSqlOS<AppDbContext>(options =>
{
    options.AuthServer.ConfigureSigningKeyCustody(custody =>
        custody.DataProtectionKeyRingIsPersistedAndShared = true);
});

var app = builder.Build();
app.MapSqlOS();
```

## Auth flow

Typical browser login:

1. App sends the user to `/sqlos/auth/authorize` with PKCE.
2. User enters email. [Home realm discovery](/docs/authserver/home-realm-discovery) picks password, Email OTP, or SSO.
3. User signs in (password, Email OTP, OIDC, or SAML).
4. Multiple orgs? User picks one.
5. MFA required? SqlOS renders or returns a TOTP challenge or forced enrollment step.
6. SqlOS returns an auth code.
7. App trades the code for access and refresh tokens.

<Callout type="tip" title="Start with owned clients first">
  For most teams, the first production flow should use a seeded or dashboard-created owned client. Add `CIMD`, `DCR`, and resource indicators only when you actually need portable or compatibility clients.
</Callout>

## SDK services

| Service | Purpose |
| --- | --- |
| `SqlOSAuthService` | Login, Email OTP, invitations, refresh, logout, token validation |
| `SqlOSAdminService` | Create orgs, users, memberships, clients, SSO |
| `SqlOSCryptoService` | Token generation, PKCE, password hashing, JWKS |
| `SqlOSHomeRealmDiscoveryService` | Route users to password or SSO by email domain |
| `SqlOSSsoAuthorizationService` | SAML SSO authorization and code exchange |
| `SqlOSOidcAuthService` | Google, Microsoft, GitHub, Apple, and custom social login |
| `SqlOSSettingsService` | Session lifetimes and security configuration |

## Signing keys and protected secrets

SqlOS stores JWT public keys, custody-provider IDs, and opaque key references in your application database. It refuses plaintext private-key rows. The built-in provider encrypts private key material with ASP.NET Core Data Protection under a purpose bound to the key ID; a custom `ISqlOSSigningKeyCustody` can keep signing operations in KMS, Vault, or an HSM.

AuthServer startup fails until custody is explicitly configured. With Data Protection, persist the key ring outside the application database, protect it at rest, and share it across all token-issuing instances. If the ring is missing, SqlOS fails closed without silently rotating the active key. See [Signing-Key Custody](/docs/authserver/signing-key-custody).

## Hosted and headless

<Accordion>
  <AccordionItem title="Hosted auth" defaultOpen>
    SqlOS renders the login, signup, invitation, OTP, and recovery pages for you. This is the fastest path for internal tools and most first-party apps.
  </AccordionItem>
  <AccordionItem title="Headless auth">
    SqlOS still runs OAuth/OIDC, sessions, and token issuance. Your application takes ownership of the login UI and interaction flow.
  </AccordionItem>
  <AccordionItem title="Client onboarding modes">
    Use seeded or dashboard-created owned clients for the normal path. Reach for CLI device flow, `CIMD`, and optional `DCR` when you need terminal, portable, or compatibility-oriented clients.
  </AccordionItem>
</Accordion>
