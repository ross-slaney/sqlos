AuthServer is SqlOS's identity piece. Users, orgs, sessions, OAuth tokens, social OIDC, and SAML run inside your app. Data lives in your database. For applications, SqlOS is an OAuth authorization server; for Google, Microsoft, Apple, and custom social login, it acts as an OIDC relying party.

## Setup

```csharp
builder.AddSqlOS<AppDbContext>();

var app = builder.Build();
app.MapSqlOS();
```

## Auth flow

Typical browser login:

1. App sends the user to `/sqlos/auth/authorize` with PKCE.
2. User chooses an enabled credential. Email-first flows use [home realm discovery](/docs/authserver/home-realm-discovery) to pick password, Email OTP, or SSO.
3. User signs in (password, email or phone OTP, OIDC, or SAML).
4. Multiple orgs? User picks one.
5. MFA required? SqlOS renders or returns a TOTP challenge or forced enrollment step.
6. SqlOS returns an auth code.
7. App trades the code for access and refresh tokens.

<Callout type="tip" title="Start with owned clients first">
  For most teams, the first production flow should use a seeded or dashboard-created owned client. Add `CIMD`, `DCR`, and resource indicators only when you actually need portable or compatibility clients.
</Callout>

## SDK services

| Service | Purpose |
| --- | --- |
| `SqlOSAuthService` | Login, email and phone OTP, invitations, refresh, logout, token validation |
| `SqlOSAdminService` | Create orgs, users, memberships, clients, SSO |
| `SqlOSCryptoService` | Token generation, PKCE, password hashing, JWKS |
| `SqlOSHomeRealmDiscoveryService` | Route users to password or SSO by email domain |
| `SqlOSSsoAuthorizationService` | SAML SSO authorization and code exchange |
| `SqlOSOidcAuthService` | Google, Microsoft, GitHub, Apple, and custom social login |
| `SqlOSSettingsService` | Session lifetimes and security configuration |

## Signing keys and protected secrets

SqlOS stores JWT signing keys in your application database. By default, private signing key PEMs are plaintext at rest in that database. Set `AuthServer.ProtectSigningKeysWithDataProtection = true` to protect them with ASP.NET Core Data Protection; enabling the option also upgrades legacy plaintext rows when the active key is loaded.

When protection is enabled, production deployments must configure a durable, shared Data Protection key ring outside the application database. If those keys are lost, protected signing keys and other protected secrets cannot be unprotected. See [Production Readiness](/docs/guides/production-readiness#5-persist-and-share-data-protection-keys) for the rollout sequence and rotation caveats.

## Hosted and headless

<Accordion>
  <AccordionItem title="Hosted auth" defaultOpen>
    SqlOS renders the login, signup, invitation, OTP, and recovery pages for you. This is the fastest path for internal tools and most first-party apps.
  </AccordionItem>
  <AccordionItem title="Headless auth">
    SqlOS still runs OAuth authorization, sessions, token issuance, and its social OIDC relying-party flows. Your application takes ownership of the login UI and interaction flow.
  </AccordionItem>
  <AccordionItem title="Client onboarding modes">
    Use seeded or dashboard-created owned clients for the normal path. Reach for CLI device flow, `CIMD`, and optional `DCR` when you need terminal, portable, or compatibility-oriented clients.
  </AccordionItem>
</Accordion>
