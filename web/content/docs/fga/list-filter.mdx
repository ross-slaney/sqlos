A list endpoint reads authorized data one page at a time: `ToPageAsync` on your EF Core query, with the subject and the permission each row needs. It returns only rows the subject may see, in your query's order. For one resource, use [`CheckAccessAsync`](/docs/fga/checking-a-permission) or [`AuthorizedDetailAsync`](/docs/fga/detail-endpoint). Those are the two ways to read authorized data.

<Callout type="warning" title="Authentication comes first">
  `ToPageAsync` authorizes a subject ID; it does not authenticate the request. Validate a bearer token for the API's exact audience before the endpoint runs, then use the validated token's user ID as the FGA subject.
</Callout>

## Pages

Page the query with the subject, the permission, a page size, and the previous page's cursor, sorted however the screen sorts:

```csharp
var page = await db.Chains
    .AsNoTracking()
    .Where(c => c.Name.Contains(search))   // your filters, any number
    .OrderBy(c => c.Name)                  // the order; the key is appended
    .ToPageAsync(subjectId, "CHAIN_VIEW", pageSize: 20, cursor: request.Cursor);

return Results.Ok(page.ToResponse(c => new ChainDto(c.Id, c.Name)));
```

`ToPageAsync` resolves the subject's principals (the subject plus its active groups) and the permission, then reads your query in its order and checks each row, in growing batches. In the same rounds it reads the caller's own rows from the node index SqlOS keeps for the entity (which rows sit under which of the caller's granted nodes, in SqlOS's own tables) and, once they fit the batch, sorts them through your query. Whichever finishes first is the page, so a caller who sees everything costs about a page and a caller who can see 3 rows of a million costs about those 3 rows, not the table. The page's rows are then loaded through your query (`Include`, tracking) and checked once more.

The query must start from a `DbSet` of a context that derives from `SqlOSDbContext<TContext>`. The node index is a table in your EF model (`SqlOSFgaPage_Chains_Id`), so your next migration creates it; `SqlOSDbContext` keeps it current in the same transaction as every save. See [Paginating authorized lists](/docs/guides/paginating-authorized-lists) for the cursor, the response, and what the query may contain.

Pass `NextCursor` back as the next request's cursor. Do not write your own position filter (`.Where(c => c.Name.CompareTo(lastSeen) > 0)`, keyset libraries, `since=` parameters): `ToPageAsync` reads from the cursor, and a hand-written position is just another filter there, so every page reads the caller's rows from the start of the order.

### What pages cost

- **Any order** costs at most about nine times the smaller of the query's rows up to the page and the rows the caller can see, plus a page: about a page for a caller who sees most rows, about its own rows for a caller who sees few, and at worst about √(rows × page size) for a caller whose rows are spread through the order (4,472 for a million rows and a page of 20).
- **A sort declared with `HasPageOrder`** costs about a page for every caller, including one whose rows sit at the far end of the order. Declare the hot sorts of large lists: see [Optimizing page performance](/docs/guides/optimizing-page-orders).

```csharp
protected override void OnApplicationModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Chain>(entity =>
    {
        entity.HasKey(c => c.Id);
        entity.Property(c => c.Name).HasMaxLength(200);
        entity.HasPageOrder(c => c.Name);   // optional: (Name, Id) costs about a page
    });
}
```

## No counts or joins

SqlOS has no authorized count, `Any`, join, or unpaged list. Each of those costs every row the caller can see, which is what pages exist to avoid. Show a page and its `HasNextPage` instead of a total, and check one resource with `CheckAccessAsync` instead of asking whether any row is visible. Sorting, search, and projection are ordinary EF Core on the query you page; project after the page with `page.ToResponse(...)`.

## Full endpoint example

From the retail example app (`examples/SqlOS.Example.Api/FgaRetail/Endpoints/ChainEndpoints.cs`):

```csharp
group.MapGet("/", async (
    ExampleAppDbContext context,
    HttpContext http,
    int pageSize = 10,
    string? search = null,
    string? cursor = null) =>
{
    var subjectId = RetailSubjectResolver.ResolveSubjectId(http);

    IQueryable<Chain> query = context.Chains.AsNoTracking();
    if (!string.IsNullOrWhiteSpace(search))
        query = query.Where(c => c.Name.ToLower().Contains(search.ToLower()));

    SqlOSCursorPage<Chain> page;
    try
    {
        page = await query.OrderBy(c => c.Name)
            .ToPageAsync(subjectId, RetailPermissionKeys.ChainView, Math.Clamp(pageSize, 1, 100), cursor, http.RequestAborted);
    }
    catch (Exception exception) when (exception is SqlOSCursorException or ArgumentException { ParamName: "cursor" })
    {
        return Results.BadRequest(new { error = SqlOSCursorException.ErrorCode, message = exception.Message });
    }

    return Results.Ok(page.ToResponse(c => new ChainDto { Id = c.Id, Name = c.Name }));
});
```

## When to use

- **List endpoints** -- page what the user can see with `ToPageAsync`
- **Search** -- combine authorization with text search and sorting in the query you page
- **Feeds and sync** -- the cursor is the sync token the client stores; see [The cursor](/docs/guides/paginating-authorized-lists#the-cursor)

For single-resource access, use [AuthorizedDetailAsync](/docs/fga/detail-endpoint). For mutations, use [CheckAccessAsync](/docs/fga/checking-a-permission).
