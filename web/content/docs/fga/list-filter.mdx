`BuildFilterAsync` returns a filter for `Where(...)`. Lists only rows the subject may see. Use it wherever authorization has to sit inside a query of your own: counts, joins, aggregates, offset pages, search.

A supported paged list uses the same filter with a declared indexed order and a `Take`. SqlOS finds and merges rows from authorized branches without first loading the caller's complete grant list. Work still depends on the caller's independently granted branches, resolved principals, and the query's filters. [Designing your resource tree](/docs/fga/designing-your-resource-tree) explains the tradeoffs; [Paginating authorized lists](/docs/guides/paginating-authorized-lists) covers the query shapes.

This is a read-side helper. Lifecycle-managed domain rows normally implement `ISqlOSResourceEntity`; the filter only needs the inherited `ResourceId` contract to tie application rows to their FGA resources.

<Callout type="warning" title="Authentication comes first">
  The filter authorizes a subject ID; it does not authenticate the request. Validate a bearer token for the API's exact audience before the endpoint runs, then use the validated token's user ID as the FGA subject.
</Callout>

## Basic usage

```csharp
var filter = await authService
    .BuildFilterAsync<Chain>(subjectId, "CHAIN_VIEW");

var chains = await dbContext.Chains
    .Where(filter)
    .OrderBy(c => c.Name)
    .ToListAsync();
```

The subject only sees chains they have access to. The filter translates to a SQL predicate -- no in-memory filtering.

## How the filter works

Every FGA resource carries its **lineage**: its ancestor at each level of the tree, its depth, and its **reach**, the highest level from which access flows down to it through active resources only. Schema v11 adds the columns to the resource table (one ancestor column per level up to the default depth of 10; a larger `MaxResourceHierarchyDepth` adds the rest at startup), SqlOS keeps them exact with triggers, and fills them once when you upgrade.

Each protected application row connects through `ResourceId` to an FGA resource. Its ancestry is stored in SqlOS's private scope index, maintained by triggers; the application table has no scope column.

Building a filter resolves the caller's principals (the subject and its active groups) and the permission, and reads no grant. The filter is evaluated by the context's query execution (`AddSqlOS` configures it; a context built by hand calls `UseSqlOSFga`) when a query over it runs, in one of two ways. A page (the filter, an order, a `Take`) is walked: SqlOS reads the caller's granted branches of the tree as it goes and does not enumerate the complete grant list up front; [Paginating authorized lists](/docs/guides/paginating-authorized-lists) covers it. Every other query (a count, a join, a list without `Take`) runs as one statement: SqlOS first reads the caller's **access roots**, the resources on which the caller, or one of their active groups, holds a current grant whose role includes the permission, and the statement then says, for each row: at the level of one of those roots, the private index's scope holds that root. A correlated SQL `EXISTS` matches it to the application row by its existing primary key, preserving application row multiplicity. Additional predicates and query shape still affect the plan.

There is one filter, whatever the number of grants. In a planned statement, a caller with several roots at a level, up to thousands of grants on single resources, gets the same test: the row's scope at that level is one of the roots, sent as one list parameter. The roots are read for every such statement, so a count or a join costs more as the caller's grants grow. A page does not have this cost: the walk reads each grant's rows from where they are and merges them in the page's order.

## The scope column

The scope column is internal to SqlOS. It records the resource type and the ancestors from which access flows down to a row. Neither `SqlOSResourceEntity` nor `IHasResourceId` adds it to application tables.

For each protected table, SqlOS maintains one `SqlOSFgaScopeIndex_*` table in its own schema. It stores the application's primary key, `ResourceId`, declared sorting columns, and scope. Per-level indexes on that table support the same branch seeks on SQL Server and PostgreSQL. Application-table triggers update this projection in the write's transaction; resource triggers update it when ancestry or visibility changes.

Initial creation builds the index from existing rows. Ordinary startup does not scan application rows to repair it. Writes must run with the maintenance triggers enabled.

Declare an index for each order you page in and end it with the key, as the [pagination guide](/docs/guides/paginating-authorized-lists) shows; SqlOS mirrors it per level. A page sorted by a column you declared no index for still returns the right rows, through the caller's whole scope rather than one seek, and SqlOS logs a warning naming the entity, the order, and the index to declare, once per query shape.

The price is storage and index maintenance: one index per level per declared order, over the rows at or below that level. The page executor also uses grant counts and direct-grant tables; [the modeling guide](/docs/fga/designing-your-resource-tree#what-sqlos-maintains-for-you) explains their storage and write implications. These are indexes for declared orders, not every possible sorting permutation.

Both the page executor and ordinary filtered statements use the projection to decide which rows are visible; the values a statement returns, keys and order columns included, are always the row's. Filtering, ordering, and aggregates still execute in the database. Its maintenance adds one shared projection entry per row, not one per principal.

## Filter lifetime

The caller's principal set (the subject plus its active group memberships) and permission are resolved when the returned task is awaited; grants are read when each query runs. Build the filter once per request and compose it into that request's queries. Do not cache it in statics or reuse it across requests, because group membership is captured at construction. The caller's own lifecycle is still checked when the query runs: a user deactivated after the filter was built sees nothing.

The filter holds no `DbContext`: compose it into a query on an instance of the same application context configured with SqlOS's query execution (`AddSqlOS` configures it; a context built by hand calls `UseSqlOSFga`), including instances from `IDbContextFactory` or a pool. List filters and point checks run in the database, so they need SQL Server or PostgreSQL; an in-memory provider fails with a message that says so.

## What determines query cost

Supported indexed pages use lineage, grant counts, and direct-grant indexes to find rows where the caller has access. They avoid enumerating the entire grant list before the page. A page across many independent inherited branches still needs to discover and merge those branches; even an empty page can need to visit them all.

Other costs remain:

- `Count()`, `Sum()`, joins, and other aggregate or non-page shapes use the SQL predicate path, including resolving access roots.
- A large `Skip(...)` makes the executor walk the skipped rows; use keyset pagination for deep lists.
- Unsupported orders, including mixed directions or an order without a suitable declared index, fall back to the predicate path.
- Filters not served efficiently by the available indexes can require examining many candidates, even on an optimized page.

One API preserves authorization semantics across these shapes; it does not make them equally cheap. See the [pagination guide](/docs/guides/paginating-authorized-lists) for exact recognition rules and diagnostics.

## Composing with plain EF

SqlOS does authorization filters only. Pagination, sorting, search, and projection are ordinary EF Core on the same query:

```csharp
var canView = await authService
    .BuildFilterAsync<InventoryItem>(subjectId, "INVENTORY_VIEW");

var items = await db.InventoryItems
    .Where(canView)
    .Where(i => i.LocationId == locationId)
    .Select(i => new InventoryItemDto
    {
        Id = i.Id,
        Name = i.Name,
        LocationName = i.Location!.Name
    })
    .OrderBy(d => d.Name).ThenBy(d => d.Id)
    .Skip(page * pageSize).Take(pageSize)
    .ToListAsync();
```

Everything composes into one SQL statement: the authorization predicate, your business predicates, the projection, the ordering, and the paging.

For cursor/keyset pagination over authorized lists, see [Paginating authorized lists](/docs/guides/paginating-authorized-lists).

## Full endpoint example

From the retail example app:

```csharp
using SqlOS.AuthServer.Extensions;
using SqlOS.Extensions;

var api = app.MapGroup("/api");

api.MapGet("/chains", async (
    ExampleAppDbContext context,
    ISqlOSFgaAuthService authService,
    HttpContext http,
    string? search, int? page, int? pageSize) =>
{
    var subjectId = http.GetSqlOSValidatedToken()?.UserId;
    if (string.IsNullOrWhiteSpace(subjectId))
        return Results.Unauthorized();

    var canView = await authService
        .BuildFilterAsync<Chain>(subjectId, RetailPermissionKeys.ChainView);

    var query = context.Chains.Where(canView);

    if (!string.IsNullOrWhiteSpace(search))
        query = query.Where(c => c.Name.Contains(search));

    var chains = await query
        .Select(c => new ChainListDto
        {
            Id = c.Id,
            Name = c.Name,
            LocationCount = c.Locations.Count
        })
        .OrderBy(d => d.Name).ThenBy(d => d.Id)
        .Skip((page ?? 0) * (pageSize ?? 20)).Take(pageSize ?? 20)
        .ToListAsync();

    return Results.Ok(chains);
});
```

## When to use

- **List endpoints** -- filter results by what the user can see
- **Search** -- combine authorization with text search and sorting
- **Dashboards** -- aggregate only accessible data

For single-resource access, use [AuthorizedDetailAsync](/docs/fga/detail-endpoint). For mutations, use [CheckAccessAsync](/docs/fga/checking-a-permission).
