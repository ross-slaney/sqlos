`BuildFilterAsync` returns a filter for `Where(...)`. Lists only rows the subject may see. Use this on list endpoints.

This is a read-side helper. Lifecycle-managed domain rows normally implement `ISqlOSResourceEntity`; the filter only needs the inherited `ResourceId` contract to join application rows to accessible FGA resources.

<Callout type="warning" title="Authentication comes first">
  The filter authorizes a subject ID; it does not authenticate the request. Validate a bearer token for the API's exact audience before the endpoint runs, then use the validated token's user ID as the FGA subject.
</Callout>

## Basic usage

```csharp
var filter = await authService
    .BuildFilterAsync<Chain>(subjectId, "CHAIN_VIEW");

var chains = await dbContext.Chains
    .Where(filter)
    .OrderBy(c => c.Name)
    .ToListAsync();
```

The subject only sees chains they have access to. The filter translates to SQL; no application-side authorization filtering is needed. This unbounded list uses the original TVF path. For an indexed page, declare its compound order and add `Take` before projecting the results, as below.

## Filter lifetime

The subject's principal set (the subject plus its active group memberships) is resolved when the returned task is awaited. Build the filter once per request and compose it into that request's queries. Do not cache the filter in statics or reuse it across requests: group membership is captured when the filter is built; current grants and principal eligibility are checked when SQL executes, on both query paths.

## Indexed pages and the TVF fallback

For a supported single-table page with a declared indexed order and `Take`, SqlOS uses shared scope indexes to seek into the caller's granted branches. The database filters each branch, removes overlapping results, sorts them, and returns the page in one SQL statement. Application tables retain their `ResourceId` link; SqlOS adds no helper columns or indexes to them. `AddSqlOS` and `SqlOSDbContext` configure the integration automatically.

For `G` eligible granted scopes and page size `k`, the query collects at most `G × k` matching candidates before deduplication and ordering. Residual application filters can examine additional authorized rows, and many independent grants still require many branch lookups. Counts, exports, unsupported compositions, and orders without a maintained index retain the TVF. That path can examine many denied rows, or the remaining table for an empty result. See [supported page shapes and costs](/docs/guides/paginating-authorized-lists).

## Composing with plain EF

Keep pagination, sorting, search, and projection in ordinary EF Core. Declare an index matching `(Name, Id)`, put the page limit on the entity query, then select the response fields:

```csharp
var canView = await authService
    .BuildFilterAsync<InventoryItem>(subjectId, "INVENTORY_VIEW");

var items = await db.InventoryItems
    .Where(canView)
    .Where(i => i.LocationId == locationId)
    .OrderBy(i => i.Name).ThenBy(i => i.Id)
    .Skip(page * pageSize).Take(pageSize)
    .Select(i => new InventoryItemDto
    {
        Id = i.Id,
        Name = i.Name,
        Price = i.Price
    })
    .ToListAsync();
```

Authorization, business predicates, ordering, and pagination stay in the database. `Skip` still pays for the skipped prefix; a keyset condition avoids that offset work. There is no separate authorization-aware page API.

For cursor/keyset pagination over authorized lists, see [Paginating authorized lists](/docs/guides/paginating-authorized-lists).

## Full endpoint example

An endpoint using the same pattern:

```csharp
using SqlOS.AuthServer.Extensions;
using SqlOS.Extensions;

var api = app.MapGroup("/api");

api.MapGet("/chains", async (
    ExampleAppDbContext context,
    ISqlOSFgaAuthService authService,
    HttpContext http,
    string? search, int? page, int? pageSize) =>
{
    var subjectId = http.GetSqlOSValidatedToken()?.UserId;
    if (string.IsNullOrWhiteSpace(subjectId))
        return Results.Unauthorized();

    var canView = await authService
        .BuildFilterAsync<Chain>(subjectId, RetailPermissionKeys.ChainView);

    var query = context.Chains.Where(canView);

    if (!string.IsNullOrWhiteSpace(search))
        query = query.Where(c => c.Name.Contains(search));

    var chains = await query
        .OrderBy(c => c.Name).ThenBy(c => c.Id)
        .Skip((page ?? 0) * (pageSize ?? 20)).Take(pageSize ?? 20)
        .Select(c => new ChainListDto
        {
            Id = c.Id,
            Name = c.Name,
            LocationCount = c.Locations.Count
        })
        .ToListAsync();

    return Results.Ok(chains);
});
```

Declare `(Name, Id)` in the `Chain` EF model for this page order. `Name.Contains(search)` and the per-row location count keep their normal database costs; the scope index does not make substring search or aggregates constant-time.

## When to use

- **List endpoints** -- filter results by what the user can see
- **Search** -- combine authorization with text search and sorting
- **Dashboards** -- aggregate only accessible data

For single-resource access, use [AuthorizedDetailAsync](/docs/fga/detail-endpoint). For mutations, use [CheckAccessAsync](/docs/fga/checking-a-permission).
