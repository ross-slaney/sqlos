`BuildFilterAsync` returns a filter for `Where(...)`. Lists only rows the subject may see. Use this on list endpoints.

This is a read-side helper. Lifecycle-managed domain rows normally implement `ISqlOSResourceEntity`; the filter only needs the inherited `ResourceId` contract to join application rows to accessible FGA resources.

<Callout type="warning" title="Authentication comes first">
  The filter authorizes a subject ID; it does not authenticate the request. Validate a bearer token for the API's exact audience before the endpoint runs, then use the validated token's user ID as the FGA subject.
</Callout>

## Basic usage

```csharp
var filter = await authService
    .BuildFilterAsync<Chain>(subjectId, "CHAIN_VIEW");

var chains = await dbContext.Chains
    .Where(filter)
    .OrderBy(c => c.Name)
    .ToListAsync();
```

The subject only sees chains they have access to. The filter translates to a SQL query -- no in-memory filtering.

## Filter lifetime

The subject's principal set (the subject plus its active group memberships) is resolved when the returned task is awaited. Build the filter once per request and compose it into that request's queries. Do not cache the filter in statics or reuse it across requests -- grant and membership changes are not reflected in an already-built filter.

## Composing with plain EF

SqlOS does authorization filters only. Pagination, sorting, search, and projection are ordinary EF Core on the same query:

```csharp
var canView = await authService
    .BuildFilterAsync<InventoryItem>(subjectId, "INVENTORY_VIEW");

var items = await db.InventoryItems
    .Where(canView)
    .Where(i => i.LocationId == locationId)
    .Select(i => new InventoryItemDto
    {
        Id = i.Id,
        Name = i.Name,
        LocationName = i.Location!.Name
    })
    .OrderBy(d => d.Name).ThenBy(d => d.Id)
    .Skip(page * pageSize).Take(pageSize)
    .ToListAsync();
```

Everything composes into one SQL statement: the authorization TVF join, your business predicates, the projection, the ordering, and the paging.

For cursor/keyset pagination over authorized lists, see [Paginating authorized lists](/docs/guides/paginating-authorized-lists).

## Listing everything a subject can see

`BuildFilterAsync` tests each candidate row the query reads. That is the right shape when the query already narrows the rows: a store's products, a search, a date range. It is the wrong shape for "everything I can see" when the subject can see little of the table, because the engine examines about `pageSize / selectivity` rows per page. A manager who may see one row in ten thousand pays about 200,000 row checks for a page of 20.

`ListVisibleAsync` answers that question from the resource closure SqlOS maintains (one row per ancestor and descendant), reading at most `pageSize` entries per grant the subject holds, whatever the table's size and however sparse the subject's access:

```csharp
var page = await authService.ListVisibleAsync<Product>(
    subjectId, "PRODUCT_VIEW", resourceTypeId: "product", pageSize: 20, cursor: request.Cursor);

return Results.Ok(new { items = page.Items, nextCursor = page.NextCursor });
```

The two paths agree row for row: a page is exactly the rows `BuildFilterAsync` would admit for that resource type, in resource creation order. `ListVisibleAsync` fixes that order and takes no other predicate; when the screen needs a different order or a filter, narrow the query by that filter and compose `BuildFilterAsync`.

The page starts from the resources and joins your entity rows by `ResourceId`, so index that column on every table you list this way (a unique index, since one resource backs one row).

| | `BuildFilterAsync` | `ListVisibleAsync` |
|---|---|---|
| Composes with | Any EF query: predicates, projections, ordering, paging | Nothing: one type, creation order, opaque cursor |
| Rows examined per page | About `pageSize / selectivity` | At most `pageSize` closure entries per grant |
| Use for | Narrowed lists, search, dashboards | "Everything I can see" lists and feeds |

## Full endpoint example

From the retail example app:

```csharp
using SqlOS.AuthServer.Extensions;
using SqlOS.Extensions;

var api = app.MapGroup("/api");

api.MapGet("/chains", async (
    ExampleAppDbContext context,
    ISqlOSFgaAuthService authService,
    HttpContext http,
    string? search, int? page, int? pageSize) =>
{
    var subjectId = http.GetSqlOSValidatedToken()?.UserId;
    if (string.IsNullOrWhiteSpace(subjectId))
        return Results.Unauthorized();

    var canView = await authService
        .BuildFilterAsync<Chain>(subjectId, RetailPermissionKeys.ChainView);

    var query = context.Chains.Where(canView);

    if (!string.IsNullOrWhiteSpace(search))
        query = query.Where(c => c.Name.Contains(search));

    var chains = await query
        .Select(c => new ChainListDto
        {
            Id = c.Id,
            Name = c.Name,
            LocationCount = c.Locations.Count
        })
        .OrderBy(d => d.Name).ThenBy(d => d.Id)
        .Skip((page ?? 0) * (pageSize ?? 20)).Take(pageSize ?? 20)
        .ToListAsync();

    return Results.Ok(chains);
});
```

## When to use

- **List endpoints** -- filter results by what the user can see
- **Search** -- combine authorization with text search and sorting
- **Dashboards** -- aggregate only accessible data

For single-resource access, use [AuthorizedDetailAsync](/docs/fga/detail-endpoint). For mutations, use [CheckAccessAsync](/docs/fga/checking-a-permission).
