`BuildFilterAsync` returns a filter for `Where(...)`. Lists only rows the subject may see. Use this on list endpoints.

This is a read-side helper. Lifecycle-managed domain rows normally implement `ISqlOSResourceEntity`; the filter only needs the inherited `ResourceId` contract to tie application rows to their FGA resources.

<Callout type="warning" title="Authentication comes first">
  The filter authorizes a subject ID; it does not authenticate the request. Validate a bearer token for the API's exact audience before the endpoint runs, then use the validated token's user ID as the FGA subject.
</Callout>

## Basic usage

```csharp
var filter = await authService
    .BuildFilterAsync<Chain>(subjectId, "CHAIN_VIEW");

var chains = await dbContext.Chains
    .Where(filter)
    .OrderBy(c => c.Name)
    .ToListAsync();
```

The subject only sees chains they have access to. The filter translates to a SQL predicate -- no in-memory filtering.

## How the filter works

Every FGA resource carries its **lineage**: its ancestor at each level of the tree, its depth, and its **reach**, the highest level from which access flows down to it through active resources only. Schema v11 adds the columns to the resource table (one ancestor column per level up to the default depth of 10; a larger `MaxResourceHierarchyDepth` adds the rest at startup), SqlOS keeps them exact with triggers, and fills them once when you upgrade.

Every entity of yours that implements `IHasResourceId` declares one more column, the **scope column** (`FgaScope`): its row's resource type and, for each level of the tree, the ancestor at that level where access flows down to the row from it. SqlOS keeps it current with triggers on your table and on the resource table, and fills it once when you upgrade. [Set up FGA](/docs/fga/setup) shows the declaration for both ways of adding SqlOS.

When you build a filter, SqlOS reads the caller's **access roots** once: the resources on which the caller, or one of their active groups, holds a current grant whose role includes the permission. The filter then says, for each row: at the level of one of those roots, the row's scope column holds that root. It is the same predicate for every caller and every table, it joins nothing, and for a caller whose access comes from one grant the database answers a page with one index seek plus the rows of the page, whatever the table's size, in any order you declared an index for.

A caller with more than 1,000 roots (thousands of grants on single resources, say) is checked row by row by `fn_IsResourceAccessible` instead, which probes the grants of each row's ancestors: the same rule, at a cost that does not depend on how many grants the caller holds.

## The scope column

The scope column is one column per table. Your entity declares it, and SqlOS manages its contents:

```csharp
public byte[]? FgaScope { get; private set; }
```

The compiler requires it: `IHasResourceId` (and `ISqlOSResourceEntity`, which extends it) has an `FgaScope` member, so an entity without it does not build. EF Core maps it like any other property, as `varbinary(512)` on SQL Server and `bytea` on PostgreSQL, the same layout on both, sized for any depth you may configure later. Your migration carries it, with an index on `ResourceId` if you declared none: the triggers find a resource's rows by it. SqlOS never writes it through EF Core, and your code never sets it.

What SqlOS creates and maintains itself at startup, outside your migrations:

- per level of the tree, an index on that level's part of the scope column followed by your primary key, and one more per index you declared on the table (the orders you page in), filtered to the rows at or below the level, so a level deeper than any row costs nothing. On PostgreSQL these are expression indexes; on SQL Server they are built on computed columns that take no storage;
- statistics on the type part of the column, so the optimizer knows the type test keeps nearly every row and walks the level's index instead of sorting the caller's whole scope;
- two triggers on your table that set a row's scope when it is inserted or its `ResourceId` changes, and the resource table's triggers that keep it current when resources move, are deactivated, retyped, or deleted;
- the one-time fill when a table first gets the column.

If a table's column is missing because its migration was not applied, SqlOS stops at startup and names the table.

Declare an index for each order you page in and end it with the key, as the [pagination guide](/docs/guides/paginating-authorized-lists) shows; SqlOS mirrors it per level. A page sorted by a column you declared no index for still returns the right rows, through the caller's whole scope rather than one seek.

The price is storage: one index per level per declared order, over the rows at or below that level. In the benchmark's 50-million-row catalog the scope column and its indexes are about half of the database.

**Upgrading**: add `public byte[]? FgaScope { get; private set; }` to every entity that implements `IHasResourceId` (the build lists them), add and apply one migration per context, and start the application. A context that uses `EnsureCreated` gets the column with its tables.

## Filter lifetime

The caller's principal set (the subject plus its active group memberships) and their grants are read when the returned task is awaited. Build the filter once per request and compose it into that request's queries. Do not cache the filter in statics or reuse it across requests -- grant and membership changes are not reflected in an already-built filter. The caller's own lifecycle is still checked when the query runs: a user deactivated after the filter was built sees nothing.

## Composing with plain EF

SqlOS does authorization filters only. Pagination, sorting, search, and projection are ordinary EF Core on the same query:

```csharp
var canView = await authService
    .BuildFilterAsync<InventoryItem>(subjectId, "INVENTORY_VIEW");

var items = await db.InventoryItems
    .Where(canView)
    .Where(i => i.LocationId == locationId)
    .Select(i => new InventoryItemDto
    {
        Id = i.Id,
        Name = i.Name,
        LocationName = i.Location!.Name
    })
    .OrderBy(d => d.Name).ThenBy(d => d.Id)
    .Skip(page * pageSize).Take(pageSize)
    .ToListAsync();
```

Everything composes into one SQL statement: the authorization predicate, your business predicates, the projection, the ordering, and the paging.

For cursor/keyset pagination over authorized lists, see [Paginating authorized lists](/docs/guides/paginating-authorized-lists).

## Full endpoint example

From the retail example app:

```csharp
using SqlOS.AuthServer.Extensions;
using SqlOS.Extensions;

var api = app.MapGroup("/api");

api.MapGet("/chains", async (
    ExampleAppDbContext context,
    ISqlOSFgaAuthService authService,
    HttpContext http,
    string? search, int? page, int? pageSize) =>
{
    var subjectId = http.GetSqlOSValidatedToken()?.UserId;
    if (string.IsNullOrWhiteSpace(subjectId))
        return Results.Unauthorized();

    var canView = await authService
        .BuildFilterAsync<Chain>(subjectId, RetailPermissionKeys.ChainView);

    var query = context.Chains.Where(canView);

    if (!string.IsNullOrWhiteSpace(search))
        query = query.Where(c => c.Name.Contains(search));

    var chains = await query
        .Select(c => new ChainListDto
        {
            Id = c.Id,
            Name = c.Name,
            LocationCount = c.Locations.Count
        })
        .OrderBy(d => d.Name).ThenBy(d => d.Id)
        .Skip((page ?? 0) * (pageSize ?? 20)).Take(pageSize ?? 20)
        .ToListAsync();

    return Results.Ok(chains);
});
```

## When to use

- **List endpoints** -- filter results by what the user can see
- **Search** -- combine authorization with text search and sorting
- **Dashboards** -- aggregate only accessible data

For single-resource access, use [AuthorizedDetailAsync](/docs/fga/detail-endpoint). For mutations, use [CheckAccessAsync](/docs/fga/checking-a-permission).
