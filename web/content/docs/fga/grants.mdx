A grant links a subject, a role, and a resource. The subject gains all permissions from the role on that resource and every descendant.

To assign one role to a team and resolve it for every current member, follow [Authorize teams with FGA groups](/docs/guides/fga-groups).

## Create a grant

**Dashboard**: Fine-Grained Auth > Grants

![Grants page](/docs/dashboard-grants.png)

**SDK**:

```csharp
await context.GrantRoleAsync(
    subjectId,
    "org::acme",
    "company_admin",
    ct);
await context.SaveChangesAsync(ct);
```

`GrantRoleAsync` is the host's way to create a grant: it checks that the subject, the role (by key or ID), and the resource exist, and tracks the grant for your next save. It also accepts an `ISqlOSResourceEntity` in place of the resource ID.

**Admin API**:

```bash
curl -X POST http://localhost:5062/sqlos/admin/fga/api/grants \
  -b "$SQLOS_DASHBOARD_COOKIE_JAR" \
  -H "Content-Type: application/json" \
  -d '{
    "subjectId": "usr_...",
    "roleId": "role_...",
    "resourceId": "org::acme"
  }'
```

A subject holds a role on a resource once per time window. `GrantRoleAsync` returns the grant the subject already has instead of adding a second one, and the Admin API answers `409 Conflict` with the existing grant's `grantId`:

```json
{ "error": "An identical grant already exists.", "grantId": "grant_..." }
```

Every grant and revocation writes an audit row, `fga.grant.created` or `fga.grant.revoked`, naming who made the change: host code, an operator, a SCIM directory, or SqlOS itself.

## Inheritance

Grants inherit downward through the resource tree:

```
org::acme              ← grant: jane / Company Admin
  ├── walmart          ← jane inherits CHAIN_VIEW, CHAIN_EDIT
  │   ├── store-001    ← jane inherits LOCATION_VIEW, LOCATION_EDIT
  │   └── store-002    ← jane inherits LOCATION_VIEW, LOCATION_EDIT
  └── target           ← jane inherits CHAIN_VIEW, CHAIN_EDIT
```

Grant at a higher level = broader access. Grant at a lower level = narrower access.

A Store Clerk granted on `store-001` can only see that one store's inventory. A Company Admin granted on `org::acme` sees everything underneath.

## Revoke a grant

**SDK**:

```csharp
await context.RevokeRoleAsync(subjectId, "org::acme", "company_admin", ct);
await context.SaveChangesAsync(ct);
```

`RevokeRoleAsync` removes the role in every time window the subject holds it.

**Admin API**:

```bash
curl -X DELETE http://localhost:5062/sqlos/admin/fga/api/grants/{grantId} \
  -b "$SQLOS_DASHBOARD_COOKIE_JAR"
```

The Admin API requires an operator session; see [Authenticate operator API calls](/docs/authserver/dashboard-overview#authenticate-operator-api-calls).

## Time-bounded grants

Grants support optional `EffectiveFrom` and `EffectiveTo` dates for temporary access. Pass them, and an optional description, in `SqlOSFgaGrantOptions`:

```csharp
await context.GrantRoleAsync(
    contractorId,
    "store-001",
    "store_manager",
    new SqlOSFgaGrantOptions
    {
        EffectiveFrom = DateTime.UtcNow,
        EffectiveTo = DateTime.UtcNow.AddMonths(3),
        Description = "Holiday cover"
    },
    ct);
await context.SaveChangesAsync(ct);
```

Both bounds are included, and a bound you leave out is open. A different window is a different grant, so a subject can hold the same role on a resource for two separate periods. The Admin API takes the same window as `effectiveFrom` and `effectiveTo` in the request body.
