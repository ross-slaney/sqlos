There are two ways to add SqlOS authorization to an EF Core application. Both give you the same `BuildFilterAsync` list filter and the same performance, on SQL Server and on PostgreSQL. Pick by who should own the FGA resource behind each row.

| | SqlOSDbContext (recommended) | Your own DbContext |
| --- | --- | --- |
| Your context | derives from `SqlOSDbContext<TContext>` | derives from `DbContext` and calls `modelBuilder.UseSqlOS(Database.ProviderName)` last in `OnModelCreating` |
| Your protected entities | derive from `SqlOSResourceEntity` (or implement `ISqlOSResourceEntity`) | implement `IHasResourceId` |
| Each row's FGA resource | created, moved, and deleted by SqlOS on `SaveChanges` | created by your code |
| Database | SQL Server or PostgreSQL | SQL Server or PostgreSQL |

## What every protected entity declares

Every protected entity carries one thing: the id of its FGA resource. An entity that derives from `SqlOSResourceEntity` carries it already and declares nothing. An entity that spends its base class elsewhere implements the interface instead:

```csharp
public string ResourceId { get; set; } = "";
```

That column, and an index on it, is all the filter needs from your table. If you declare no index on `ResourceId`, SqlOS adds one to the EF model (`IX_{Table}_SqlOSFgaResourceId`), so your migration creates it. Nothing else of SqlOS's is on your table: no column, no trigger, no index of its own. Everything `BuildFilterAsync` reads lives on SqlOS's resources table, which holds the tree's closure. A page of a list costs about the page for a caller who sees most of the table and about the caller's rows for one who sees a sliver, whether the table holds a thousand rows or fifty million; for callers in between, the worst page grows with the square root of the table, not with the table. [List filtering](/docs/fga/list-filter) explains how, and the one case that costs more.

## Option 1: SqlOSDbContext and SqlOSResourceEntity

The entity describes its resource; SqlOS creates and maintains it. Derive from `SqlOSResourceEntity` and override what describes the resource — the resource id comes with the base class, and the members you override are never columns of your table:

```csharp
using Microsoft.EntityFrameworkCore;
using SqlOS;
using SqlOS.Fga;

public sealed class Project : SqlOSResourceEntity
{
    public Guid Id { get; set; }
    public string Name { get; set; } = "";
    public string WorkspaceResourceId { get; set; } = "";

    public override string ResourceTypeId => "project";
    public override string ResourceName => Name;
    public override string? ParentResourceId => WorkspaceResourceId;
}

public sealed class AppDbContext(DbContextOptions<AppDbContext> options)
    : SqlOSDbContext<AppDbContext>(options)
{
    public DbSet<Project> Projects => Set<Project>();

    protected override void OnApplicationModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Project>(entity =>
        {
            entity.HasKey(project => project.Id);
            entity.HasIndex(project => project.ResourceId).IsUnique();
            entity.HasIndex(project => new { project.Name, project.Id });   // an order you page in
        });
    }
}
```

Saving a `Project` creates its FGA resource under its workspace in the same `SaveChanges`.

An entity whose base class is already spoken for implements `ISqlOSResourceEntity` itself and declares `ResourceId` as [above](#what-every-protected-entity-declares); SqlOS treats both forms the same. Map the entities, never the base class: a `DbSet<SqlOSResourceEntity>` fails at model building with an error saying so.

## Option 2: your own DbContext and IHasResourceId

Your context keeps its own base class and calls SqlOS's model method as the last line of `OnModelCreating`. Your code creates each row's FGA resource.

```csharp
using Microsoft.EntityFrameworkCore;
using SqlOS.AuthServer.Interfaces;
using SqlOS.Extensions;
using SqlOS.Fga.Interfaces;

public sealed class Ticket : IHasResourceId
{
    public Guid Id { get; set; }
    public string ResourceId { get; set; } = "";
    public string Title { get; set; } = "";
}

public sealed class AppDbContext(DbContextOptions<AppDbContext> options)
    : DbContext(options), ISqlOSAuthServerDbContext, ISqlOSFgaDbContext
{
    public DbSet<Ticket> Tickets => Set<Ticket>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Ticket>(entity =>
        {
            entity.HasKey(ticket => ticket.Id);
            entity.HasIndex(ticket => ticket.ResourceId).IsUnique();
        });

        modelBuilder.UseSqlOS(Database.ProviderName);   // SqlOS's auth and FGA model, last
    }
}
```

Create the resource when you create the row:

```csharp
var id = Guid.NewGuid();
await db.CreateResourceWithIdAsync($"ticket::{id:D}", "ticket", "Printer jam", parentResourceId: workspaceResourceId);
db.Tickets.Add(new Ticket { Id = id, ResourceId = $"ticket::{id:D}", Title = "Printer jam" });
await db.SaveChangesAsync();
```

`UseSqlOS` applies SqlOS's auth and FGA model and adds the `ResourceId` index to every entity configured before it that declared none, so call it last. The two interfaces need nothing beyond what `DbContext` already has. A context you build yourself (not through `AddSqlOS`) needs nothing more: the filter is a predicate over a function in SqlOS's model, and any provider options that reach SQL Server or PostgreSQL run it.

Keep every protected entity in the context you register with `AddSqlOS`: the filter is built for that context's model. `BuildFilterAsync` names an entity outside it in its error.

## Register SqlOS on SQL Server or PostgreSQL

Both options register the same way. The provider call is the only line that differs between the databases.

```csharp
builder.AddSqlOS<AppDbContext>(
    db => db.UseSqlServer(connectionString),   // SQL Server
    // db => db.UseNpgsql(connectionString),   // PostgreSQL
    options =>
    {
        options.AuthServer.PublicOrigin = "https://app.example.com";
        options.AuthServer.Issuer = "https://app.example.com/sqlos/auth";

        options.Fga.Seed(seed =>
        {
            seed.ResourceType("project", "Project");
            seed.Permission("project.read", "Read project", "project");
            seed.Role("project_reader", "Project reader").Can("project.read");
        });
    });
```

## Create the tables, then start

1. Add a migration for your context (`dotnet ef migrations add AddProjects`) and apply it, or call `EnsureCreated` in development. The migration carries your tables, with an index on `ResourceId` if you declared none.
2. Start the application. SqlOS creates or upgrades its own tables, then the ancestor columns of its resources table with one index per level, its seven functions (`fn_ActiveSubjects`, `fn_AccessRoots`, `fn_ListVisible`, `fn_VisibleSet`, `fn_ListFirst`, `fn_IsResourceAccessible`, `fn_CheckRow`), the two lineage procedures, the two triggers on the resources table and the one on the grants table, and builds the lineage once if it was never built. None of that is in your migrations, and none of it touches your tables.

The two steps run in either order. Nothing of SqlOS's depends on your tables, so SqlOS can start before your migrations (the order the [production guide](/docs/guides/production-readiness#6-roll-schema-changes-forward-through-one-instance) gives an application whose migrations reference SqlOS's tables), and there is no per-start pass over your tables afterwards. A row is visible as soon as its resource is, however it was written: through EF Core, `ExecuteUpdate`, raw SQL or a bulk load.

SqlOS keeps the resource tree's closure current through every change: inserts, moves, deactivations, and transactions running at the same time. See [Resource hierarchy](/docs/fga/resource-hierarchy#changes-made-at-the-same-time) for the one isolation rule: change resources in `READ COMMITTED` (the default) or `SERIALIZABLE` transactions. SqlOS refuses `REPEATABLE READ` on PostgreSQL and `SNAPSHOT` on SQL Server with a clear error.

## Filter a list

The same code for both options and both databases:

```csharp
var filter = await authorization.BuildFilterAsync<Project>(subjectId, "project.read");

var page = await db.Projects
    .AsNoTracking()
    .Where(filter)
    .OrderBy(project => project.Name).ThenBy(project => project.Id)
    .Take(25)
    .ToListAsync(cancellationToken);
```

Page in an order you declared an index for, ended by the key, as above. `BuildFilterAsync` asks the database how many rows the caller sees, up to a cap. For a caller who sees many, the database walks that index from the cursor, checks each row, and stops when the page is full. For a caller who sees few, it lists their rows through the resources table's per-level indexes and sorts them. A page sorted by a column you declared no index for still returns the right rows; the database sorts every row the filter passes, which for a caller who sees many rows means checking the whole table. The filter is a predicate; it runs on any instance of the context, from `AddSqlOS`, a factory or a pool. See [List filtering](/docs/fga/list-filter) for how the filter works and what it costs.

## Upgrading from 8.0

Not supported in place; there are no compatibility shims. Either recreate the database, or remove what 8.0 put on your tables by hand: delete the `FgaScope` property from every entity (nothing declares it now), add and apply an EF migration that drops the column, and drop 8.0's per-table objects (triggers `TR_*_SqlOSFgaScope_*`, indexes `IX_*_FgaScope*`, computed columns `FgaScope*`, statistics `ST_*_FgaScopeType`) and its tables in SqlOS's schema (`SqlOSFgaDirect_*`, `SqlOSFgaGrantCounts`, `SqlOSFgaScopeTables`). SqlOS neither creates nor looks for any of them.
