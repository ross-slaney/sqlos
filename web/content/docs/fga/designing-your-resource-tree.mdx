Your application can have one document list, one inspections screen, or one work queue for everyone. A company administrator, a department manager, and an external reviewer use the same endpoint; their grants determine which records it returns.

SqlOS makes that possible by treating access as part of your data model. **Put resources beneath the place where their access belongs, then grant roles at that boundary.** You do not need a different authorization predicate for every persona.

![An application root contains two workspaces with two documents each. A team grant on Workspace A reaches Documents A and B. The same document query returns A through D for a root administrator, A and B for the team, and only D for a guest granted that document.](/docs/fga-resource-tree.png)

All three example roles include `document.read`. The team has no access to Workspace B's documents from its Workspace A grant. The guest's grant on Document D does not authorize Workspace B or Document C. Grants may belong to users, groups, service accounts, or agents; being named an administrator or owning a workspace does not create a grant automatically.

## Start with the access boundary

For a document editor, create a personal workspace when someone signs up, grant them a role containing `document.read` on it, and place their documents beneath it. A new document inherits that access without another grant. When the product adds teams, grant the appropriate role to a group on a shared workspace. Share one document with an outside reviewer by granting a narrower role on that document.

The same design applies beyond documents:

| Application | Example resource tree | A useful grant boundary |
| --- | --- | --- |
| Inspections | Organization → team → inspection → item | Team for supervisors; inspection for an assigned reviewer |
| Case management | Agency → department → case → record | Department for staff; case for outside collaborators |
| Retail | Company → region → store → inventory item | Region for managers; store for clerks |
| Document editing | Application → workspace → document | Workspace for members; document for an individual share |

A resource has one parent. Choose the parent for **permission inheritance**, not simply because two records have a foreign key relationship. Other relationships can remain ordinary application relationships. If access must arrive through two independent branches, model the additional access with grants or groups; the resource tree itself is not a multi-parent graph.

## Grant at the highest node that matches the intended access

One workspace grant can cover its current and future documents. It is easier to administer than creating a grant for every document, and the page executor can read that authorized branch through its index.

“Highest” is relative to the access you mean to give. A department reviewer should receive a department grant, not a root grant. A collaborator who may read one document should receive a document grant, not a workspace grant. **Do not broaden access just to reduce the number of grants.**

Roles supply permissions; placement supplies scope. A workspace role may contain `document.read` without `document.edit`. A permission restricted to the document resource type authorizes documents beneath the workspace, not every other kind of descendant. Access flows down through active resources, never up or sideways. An inactive resource interrupts inheritance from above; grants below it can still authorize active descendants. See [resource hierarchy](/docs/fga/resource-hierarchy) and [permissions](/docs/fga/permissions).

Use a [group](/docs/guides/fga-groups) when several subjects should share the same access. Grant to the group once and manage its membership. This avoids duplicating the grant for every member, but a group with grants on 100 independent branches still represents 100 branches.

## Keep the query about the screen

```csharp
var canRead = await authorization.BuildFilterAsync<Document>(
    subjectId, "document.read");

var documents = await db.Documents
    .Where(canRead)
    .OrderBy(d => d.Name).ThenBy(d => d.Id)
    .Take(21)
    .ToListAsync();
```

The same query serves the three callers in the diagram. It needs no `OwnerId == subjectId` or `TenantId == tenantId` condition to discover their authorized documents. Add a workspace or tenant condition when the **screen itself** is scoped there; it is a product filter, not a replacement for authorization. Authentication still happens at the request boundary, and writes still need the appropriate permission check.

For this compound order, declare the matching EF index, for example `HasIndex(d => new { d.Name, d.Id })`. Keep the returned authorization expression as its own `Where`; compose other conditions in additional `Where` calls. Ask for one extra row to detect another page, and use a keyset cursor for subsequent pages. [Paginating authorized lists](/docs/guides/paginating-authorized-lists) explains the supported query shapes and cursor forms.

## The performance tradeoff is part of the model

SqlOS maintains ancestry and indexes so a supported page can find authorized branches without first loading every grant or walking the entire application table looking for allowed rows. It trades extra database storage, write maintenance, and several coordinated SQL statements for that ability.

| Design choice | What you gain | What still costs work |
| --- | --- | --- |
| A workspace or department grant | One grant covers a growing branch; adding descendants does not require a grant for each one | Tree navigation, index lookups, and the rows the query needs |
| Grants on many independent branches | Correct global ordering across everything the caller may access | Discovering and merging those branches, even when a page is small or empty |
| Grants on individual resources | Direct-grant indexes stream those rows in a supported order without listing all grants first | Principal and role streams, query predicates, and maintaining the direct entries |
| A group grant | Shared access without a grant for every member | Resolving memberships; the group's independent branches still contribute work |
| Declared page indexes | SQL can seek into each branch in the requested order | Index storage and write maintenance multiply with hierarchy depth and declared orders |
| Ordinary EF composition | One `BuildFilterAsync` API for pages, counts, joins, and reports | These query shapes do not all use the optimized page executor |

The remaining branch cost belongs to **this caller's access**, including their groups. It is not a scan of every unrelated row in the database. A manager of one department and a collaborator on thousands of separately granted projects can therefore have different page costs even when they see the same number of records. Later pages and empty results can still need to visit those branches; a cursor does not automatically eliminate them.

This is not a guarantee that every query costs only its page size. Database filters, joins, sorting, and aggregates keep their normal costs. Even an indexed page can examine many authorized candidates if an additional filter is poorly served by its index. Current optimized pages require a supported order backed by a declared index, with all sort columns in the same direction. Other valid EF query shapes use the authorization predicate; that path resolves the caller's access roots and lets the database plan the query.

## What SqlOS maintains for you

Your application keeps ordinary tables and relationships, with `ResourceId` and the managed `FgaScope` column on protected entities. SqlOS owns the supporting lineage, per-level indexes, grant counts, direct-grant tables, and their triggers. There is no private copy of every visible row for every caller, and no index for every possible sorting permutation. Indexes follow the orders declared in your model.

The page executor runs in the application and coordinates SQL statements. It holds candidate keys and sort values for the current page, then sends unused candidates back to the database to merge with newly fetched candidates. **The database applies filtering and ordering, including its own collation and type rules.** This uses temporary application RAM and network traffic proportional to the active streams and their buffered candidates, not a copy of the entire table. The buffer is discarded after the page; later requests start fresh.

| Operation | Maintenance to account for |
| --- | --- |
| Add a resource or protected row | Derive its ancestry/scope and maintain the relevant indexes. Rows attached directly to a granted resource also create direct-index entries for those grants. Inherited workspace access does not create an entry per workspace member. |
| Change an indexed sort value or a row's resource | Update the row's indexes and matching direct-grant entries. Many separate direct grants on that resource can make this a larger write. |
| Grant, revoke, or change a grant | Adjust counts along the resource's ancestry and maintain direct entries for rows attached to that resource. This is not a per-descendant grant expansion. |
| Move, deactivate, or reactivate a branch | Refresh affected descendant lineage/scopes and direct entries, and rebuild counts for affected principals. Large changes can block concurrent writes; schedule large reorganizations accordingly. |
| A scheduled grant opens or expires | Refresh affected principals' counts. A page can perform an overdue refresh before walking, so that request may do more work. |
| Add protected tables/indexes or upgrade supporting structures | Startup may build indexes and rebuild derived state. Plan for this work on a large database. |

Keep the hierarchy stable when possible. Changing a document's title is an ordinary row update; moving a large department beneath another organization changes inherited access and can affect its entire subtree. Treat those as different operations in your product design. Do not bypass SqlOS's maintenance triggers during bulk changes without following the documented rebuild procedure.

For production, exercise the access patterns your application actually creates: one broad grant, sparse individual shares, several independent workspaces, later cursors, and empty results. The `SqlOS.Fga` logs expose page rounds, fetched candidates, and retained candidates, and explain failures to plan a recognized page shape. These help distinguish authorization traversal from the normal cost of a query's filters and indexes.
