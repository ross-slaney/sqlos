Your application can have one document list, one inspections screen, or one work queue for everyone. A company administrator, a department manager, and an external reviewer use the same endpoint; their grants determine which records it returns.

SqlOS makes that possible by treating access as part of your data model. **Put resources beneath the place where their access belongs, then grant roles at that boundary.** You do not need a different authorization predicate for every persona.

![An application root contains two workspaces with two documents each. A team grant on Workspace A reaches Documents A and B. The same document query returns A through D for a root administrator, A and B for the team, and only D for a guest granted that document.](/docs/fga-resource-tree.png)

All three example roles include `document.read`. The team has no access to Workspace B's documents from its Workspace A grant. The guest's grant on Document D does not authorize Workspace B or Document C. Grants may belong to users, groups, service accounts, or agents; being named an administrator or owning a workspace does not create a grant automatically.

## Start with the access boundary

For a document editor, create a personal workspace when someone signs up, grant them a role containing `document.read` on it, and place their documents beneath it. A new document inherits that access without another grant. When the product adds teams, grant the appropriate role to a group on a shared workspace. Share one document with an outside reviewer by granting a narrower role on that document.

The same design applies beyond documents:

| Application | Example resource tree | A useful grant boundary |
| --- | --- | --- |
| Inspections | Organization → team → inspection → item | Team for supervisors; inspection for an assigned reviewer |
| Case management | Agency → department → case → record | Department for staff; case for outside collaborators |
| Retail | Company → region → store → inventory item | Region for managers; store for clerks |
| Document editing | Application → workspace → document | Workspace for members; document for an individual share |

A resource has one parent. Choose the parent for **permission inheritance**, not simply because two records have a foreign key relationship. Other relationships can remain ordinary application relationships. If access must arrive through two independent branches, model the additional access with grants or groups; the resource tree itself is not a multi-parent graph.

## Grant at the highest node that matches the intended access

One workspace grant can cover its current and future documents. It is easier to administer than creating a grant for every document.

“Highest” is relative to the access you mean to give. A department reviewer should receive a department grant, not a root grant. A collaborator who may read one document should receive a document grant, not a workspace grant. **Do not broaden access just to reduce the number of grants.**

Roles supply permissions; placement supplies scope. A workspace role may contain `document.read` without `document.edit`. A permission restricted to the document resource type authorizes documents beneath the workspace, not every other kind of descendant. Access flows down through active resources, never up or sideways. An inactive resource interrupts inheritance from above; grants below it can still authorize active descendants. See [resource hierarchy](/docs/fga/resource-hierarchy) and [permissions](/docs/fga/permissions).

Use a [group](/docs/guides/fga-groups) when several subjects should share the same access. Grant to the group once and manage its membership. This avoids duplicating the grant for every member, but a group with grants on 100 independent branches still represents 100 branches.

## Keep the query about the screen

```csharp
var canRead = await authorization.BuildFilterAsync<Document>(
    subjectId, "document.read");

var documents = await db.Documents
    .Where(canRead)
    .OrderBy(d => d.Name).ThenBy(d => d.Id)
    .Take(21)
    .ToListAsync();
```

The same query serves the three callers in the diagram. It needs no `OwnerId == subjectId` or `TenantId == tenantId` condition to discover their authorized documents. Add a workspace or tenant condition when the **screen itself** is scoped there; it is a product filter, not a replacement for authorization. Authentication still happens at the request boundary, and writes still need the appropriate permission check.

For this compound order, declare the matching EF index, for example `HasIndex(d => new { d.Name, d.Id })`. Ask for one extra row to detect another page, and use a keyset cursor for subsequent pages. [Paginating authorized lists](/docs/guides/paginating-authorized-lists) explains ordinary EF pagination and cursor forms.

## Query performance

`BuildFilterAsync` resolves the caller's principals and returns a predicate. EF translates it to the recursive authorization TVF in the same SQL query as the application's filters, ordering, and pagination. The function walks a candidate resource's ancestors to find a matching current grant; SqlOS does not choose between query strategies using a visibility count.

A caller who can see most candidates can fill a page quickly. Sparse access can require checking many denied rows, and an empty or underfull page can examine the entire remaining table. A matching sorting index and keyset cursor avoid some ordinary sorting and offset costs, but do not eliminate this authorization cost. Counts, joins, and reports also depend on the work in the database query.

Grant placement should express the intended access. It is not a guarantee that a workspace grant makes every list query independent of table size. Test broad access, sparse individual shares, later cursors, and empty results using your application's real filters and orders.

## What SqlOS maintains for you

Your application keeps ordinary tables and relationships, connected to FGA through `ResourceId`. Entities implementing `ISqlOSResourceEntity` describe their resource and parent; `SqlOSDbContext<TContext>` synchronizes those resource rows during saves. Grants remain explicit.

SqlOS owns its resource, principal, group, role, permission, and grant tables and the authorization functions. It does not maintain application scope columns, per-level page indexes, grant-count caches, or direct-grant page tables. Application sorting and filtering stay with the database through ordinary EF queries.

Changing a resource's parent changes which ancestor grants can apply on subsequent queries. Keep hierarchy changes deliberate because they change access, and check the appropriate permissions before making them. Build the authorization filter per request so principal and group resolution is current.
