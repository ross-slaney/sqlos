Your application can have one document list, one inspections screen, or one work queue for everyone. A company administrator, a department manager, and an external reviewer use the same endpoint; their grants determine which records it returns.

SqlOS makes that possible by treating access as part of your data model. **Put resources beneath the place where their access belongs, then grant roles at that boundary.** You do not need a different authorization predicate for every persona.

![An application root contains two workspaces with two documents each. A team grant on Workspace A reaches Documents A and B. The same document query returns A through D for a root administrator, A and B for the team, and only D for a guest granted that document.](/docs/fga-resource-tree.png)

All three example roles include `document.read`. The team has no access to Workspace B's documents from its Workspace A grant. The guest's grant on Document D does not authorize Workspace B or Document C. Grants may belong to users, groups, service accounts, or agents; being named an administrator or owning a workspace does not create a grant automatically.

## Start with the access boundary

For a document editor, create a personal workspace when someone signs up, grant them a role containing `document.read` on it, and place their documents beneath it. A new document inherits that access without another grant. When the product adds teams, grant the appropriate role to a group on a shared workspace. Share one document with an outside reviewer by granting a narrower role on that document.

The same design applies beyond documents:

| Application | Example resource tree | A useful grant boundary |
| --- | --- | --- |
| Inspections | Organization → team → inspection → item | Team for supervisors; inspection for an assigned reviewer |
| Case management | Agency → department → case → record | Department for staff; case for outside collaborators |
| Retail | Company → region → store → inventory item | Region for managers; store for clerks |
| Document editing | Application → workspace → document | Workspace for members; document for an individual share |

A resource has one parent. Choose the parent for **permission inheritance**, not simply because two records have a foreign key relationship. Other relationships can remain ordinary application relationships. If access must arrive through two independent branches, model the additional access with grants or groups; the resource tree itself is not a multi-parent graph.

## Grant at the highest node that matches the intended access

One workspace grant can cover its current and future documents. It is easier to administer than creating a grant for every document, and SqlOS finds every document beneath it in one range of one index.

“Highest” is relative to the access you mean to give. A department reviewer should receive a department grant, not a root grant. A collaborator who may read one document should receive a document grant, not a workspace grant. **Do not broaden access just to reduce the number of grants.**

Roles supply permissions; placement supplies scope. A workspace role may contain `document.read` without `document.edit`. A permission restricted to the document resource type authorizes documents beneath the workspace, not every other kind of descendant. Access flows down through active resources, never up or sideways. An inactive resource interrupts inheritance from above; grants below it can still authorize active descendants. See [resource hierarchy](/docs/fga/resource-hierarchy) and [permissions](/docs/fga/permissions).

Use a [group](/docs/guides/fga-groups) when several subjects should share the same access. Grant to the group once and manage its membership. This avoids duplicating the grant for every member, but a group with grants on 100 independent branches still represents 100 branches.

## Keep the query about the screen

```csharp
var canRead = await authorization.BuildFilterAsync<Document>(
    subjectId, "document.read");

var documents = await db.Documents
    .Where(canRead)
    .OrderBy(d => d.Name).ThenBy(d => d.Id)
    .Take(21)
    .ToListAsync();
```

The same query serves the three callers in the diagram. It needs no `OwnerId == subjectId` or `TenantId == tenantId` condition to discover their authorized documents. Add a workspace or tenant condition when the **screen itself** is scoped there; it is a product filter, not a replacement for authorization. Authentication still happens at the request boundary, and writes still need the appropriate permission check.

For this compound order, declare the matching EF index, for example `HasIndex(d => new { d.Name, d.Id })`. Compose other conditions in additional `Where` calls. Ask for one extra row to detect another page, and use a keyset cursor for subsequent pages. [Paginating authorized lists](/docs/guides/paginating-authorized-lists) explains the query shapes and cursor forms.

## The performance tradeoff is part of the model

SqlOS keeps the tree's closure on its own resources table: every resource's ancestor at each level, with one index per level. Before a list runs, SqlOS asks the database how many rows this caller sees, counted up to a cap that grows with the square root of the table. A caller below the cap has their rows listed first, from their grants, and sorted. A caller at or above it has the table read in the page's order, each row checked, until the page is full. So a page costs about the caller's rows for one who sees few and about the page for one who sees most of the table. [List filtering](/docs/fga/list-filter#what-determines-query-cost) gives the cost of each.

| Design choice | What you gain | What still costs work |
| --- | --- | --- |
| A workspace or department grant | One grant covers a growing branch; adding descendants does not require a grant for each one | The rows beneath the grant when they are few; when they are many, the rows read in the page's order until the page is full |
| Grants on many independent branches | Correct global ordering across everything the caller may access | Below the cap, one index range per branch and a sort of their rows, on every page; above it, each row checked |
| Grants on individual resources | Share one document without widening the workspace grant | One index read per grant, inside the database, up to the cap |
| A group grant | Shared access without a grant for every member | Resolving memberships; the group's branches cost what the caller's own would |
| A declared index for the page's order | When rows are checked, the database seeks to the cursor and reads forward | Index storage and maintenance, as for any index you declare |
| Ordinary EF composition | One `BuildFilterAsync` API for pages, counts, joins, and reports | A count or a join reads every visible row, which for a caller who sees many rows means the whole table; a page reads the caller's rows, or reads in order until it is full |

The cost belongs to **this caller's access**, including their groups, and to the page; it is not a scan of every unrelated row in the database. A manager of one department and a collaborator on thousands of separately granted projects can have different page costs even when they see the same number of records. The worst page is a caller who sees about the cap's worth of rows, where the two ways cost about the same; it grows with the square root of the table, not with the table.

One case is worse. A caller who sees many rows, all at the far end of the page's order (a customer who has added nothing for years, listing their rows newest first), has every row before theirs read and checked. Only an index on your table ordered by who can see each row, then by the sort column, would avoid that, and SqlOS puts nothing on your tables. When the screen is scoped to that customer, a condition on your own column with an index that leads with it does the job; see [List filtering](/docs/fga/list-filter#what-determines-query-cost).

Database filters, joins, sorting, and aggregates keep their normal costs. A page over a condition the sort index cannot narrow examines more candidates than it returns, as any EF query would.

## What SqlOS maintains for you

Your application keeps ordinary tables and relationships, with a `ResourceId` column and an index on it on each protected entity. SqlOS owns its resources table with the closure (`Seq`, `Depth`, `Reach`, one ancestor column per level), one index per level, the functions the filter reads, and the two triggers that keep the closure exact. Nothing of SqlOS's is on your tables. There is no private copy of every visible row for every caller, and no index for every possible sorting permutation; the indexes on your tables are the ones you declare.

| Operation | Maintenance to account for |
| --- | --- |
| Add a resource or protected row | One resources row, its closure computed from its parent; your row is an ordinary insert |
| Change a sort value or a row's resource | An ordinary row update; nothing of SqlOS's changes |
| Grant, revoke, or change a grant | One grants row; no lineage work. The next query sees it |
| Move, deactivate, or reactivate a branch | Recompute the closure of the subtree beneath it, under a lock that other tree changes wait for; schedule large reorganizations accordingly |
| A scheduled grant opens or expires | Nothing; the dates are read when a query runs |
| Raise `MaxResourceHierarchyDepth`, or upgrade | Startup adds the ancestor columns and their indexes once; on a large resources table that takes minutes, once |

Keep the hierarchy stable when possible. Changing a document's title is an ordinary row update; moving a large department beneath another organization changes inherited access and rewrites the closure of its entire subtree. Treat those as different operations in your product design. A bulk load of resources that bypasses the triggers must run the rebuild procedure afterwards; see [Resource hierarchy](/docs/fga/resource-hierarchy#the-lineage).

For production, exercise the access patterns your application actually creates: one broad grant, sparse individual shares, several independent workspaces, later cursors, and empty results, and read the plans the database runs for them, as you would for any query. `tests/SqlOS.Benchmarks` does this for the shipped schema on both engines.
