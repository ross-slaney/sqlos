Resources are a tree. One parent per node; root has none. For access checks, FGA walks **up** from the target node to root and looks for grants.

## Tree structure

Model your app's hierarchy as nested resources:

```
root
├── org::acme (Organization)
│   ├── workspace::1 (Workspace)
│   │   └── document::1 (Document)
│   └── workspace::2 (Workspace)
└── org::globex (Organization)
    └── workspace::3 (Workspace)
```

## Entity-backed hierarchy

For protected application rows, implement `ISqlOSResourceEntity` and return the parent resource ID from `ParentResourceId`.

```csharp
public sealed class Workspace : ISqlOSResourceEntity
{
    public Guid Id { get; set; }
    public string ResourceId { get; set; } = "";
    public byte[]? FgaScope { get; private set; }
    public string OrganizationId { get; set; } = "";
    public string Name { get; set; } = "";

    public string ResourceTypeId => "workspace";
    public string ResourceName => Name;
    public string ParentResourceId => $"org::{OrganizationId}";
    public string? ResourceDescription => null;
    public bool ResourceIsActive => true;
}
```

When the entity is saved, `SqlOSDbContext<TContext>` creates or updates the resource at that point in the hierarchy.

```csharp
db.Workspaces.Add(new Workspace
{
    Id = workspaceId,
    ResourceId = $"workspace::{workspaceId:D}",
    OrganizationId = organizationId,
    Name = "Operations"
});

await db.SaveChangesAsync(ct);
```

## Non-entity roots

Use manual resource APIs for hierarchy nodes that are not application rows, such as tenant or organization roots:

```csharp
await db.ProvisionResourceWithIdAsync(
    $"org::{organization.Id}",
    "organization",
    organization.Name,
    parentResourceId: "root",
    cancellationToken: ct);
```

## How inheritance works

When checking `WORKSPACE_VIEW` on `workspace::1`:

1. Check grants directly on `workspace::1`.
2. Check grants on `org::acme`.
3. Check grants on `root`.
4. If any ancestor has a grant with a role that includes `WORKSPACE_VIEW`, access is allowed.

This means a single grant at the organization level can authorize resources underneath it without creating per-resource grants.

An inactive resource cuts the chain: a grant above it does not reach anything beneath it, and the inactive resource itself is denied.

## The lineage

SqlOS does not walk the tree at query time. Every resource carries its **lineage**: its ancestor at each level of the tree (`Ancestor0` is the top of its tree, `Ancestor1` the next level down, and so on, up to the configured `MaxResourceHierarchyDepth`), its `Depth`, and its `Reach`, the highest level from which access flows down to it through active resources only. A resource that is inactive, lies in a cycle, or sits deeper than the configured depth has no reach, and is denied.

With the lineage, "is `workspace::1` under a grant on `org::acme`" is one comparison: `workspace::1`'s ancestor at level 1 is `org::acme`, and its reach includes level 1. That is what [`BuildFilterAsync`](/docs/fga/list-filter) and `fn_IsResourceAccessible` evaluate.

Triggers on the resources table keep the lineage exact. The cost of each operation:

| Operation | What SqlOS does | Cost |
|---|---|---|
| Create a resource | Computes its lineage from its parent | One row |
| Grant or revoke | Nothing: grants are not part of the lineage | Nothing |
| Change a resource's type | Updates the scope column of its application rows | Its rows |
| Move a resource to another parent | Recomputes the subtree beneath it, level by level | The subtree |
| Deactivate or reactivate a resource | Recomputes the reach of the subtree beneath it | The subtree |
| Delete a resource | Clears its application rows' scope column | Its rows |
| A move that would create a cycle, or place a resource deeper than the configured depth | Rejects the statement | — |
| First start after upgrading, or a changed depth | Fills the lineage once: the internal nodes level by level, then every range of 500,000 resources in its own transaction | The whole table, once |

Every operation above also updates the [scope column](/docs/fga/list-filter#the-scope-column) of the application rows of the resources it touched.

Bulk loads that skip triggers must fill the lineage themselves or run the rebuild procedure afterwards (`sp_SqlOSFgaResources_LineageRebuild` on SQL Server, `fn_SqlOSFgaResources_LineageRebuild()` on PostgreSQL). The rebuild writes the whole table once, in ranges of 500,000 resources on SQL Server (each range its own transaction, so the log stays small at any size) and in one transaction on PostgreSQL. A rebuild that fails part-way is run again at the next start: SqlOS records the routines as current only after it completes.
