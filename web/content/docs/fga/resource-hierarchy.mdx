Resources are a tree. One parent per node; a root has none. Access checks look for a usable grant on the target or its ancestors using the maintained lineage.

Start with [Designing your resource tree](/docs/fga/designing-your-resource-tree) for workspace, department, and team examples, plus the read/write tradeoffs that should guide your model. This page explains how SqlOS represents and maintains that hierarchy.

## Tree structure

Model your app's hierarchy as nested resources:

```
root
├── org::acme (Organization)
│   ├── workspace::1 (Workspace)
│   │   └── document::1 (Document)
│   └── workspace::2 (Workspace)
└── org::globex (Organization)
    └── workspace::3 (Workspace)
```

## Entity-backed hierarchy

For protected application rows, implement `ISqlOSResourceEntity` and return the parent resource ID from `ParentResourceId`.

```csharp
public sealed class Workspace : ISqlOSResourceEntity
{
    public Guid Id { get; set; }
    public string ResourceId { get; set; } = "";
    public string OrganizationId { get; set; } = "";
    public string Name { get; set; } = "";

    public string ResourceTypeId => "workspace";
    public string ResourceName => Name;
    public string ParentResourceId => $"org::{OrganizationId}";
    public string? ResourceDescription => null;
    public bool ResourceIsActive => true;
}
```

When the entity is saved, `SqlOSDbContext<TContext>` creates or updates the resource at that point in the hierarchy.

```csharp
db.Workspaces.Add(new Workspace
{
    Id = workspaceId,
    ResourceId = $"workspace::{workspaceId:D}",
    OrganizationId = organizationId,
    Name = "Operations"
});

await db.SaveChangesAsync(ct);
```

## Non-entity roots

Use manual resource APIs for hierarchy nodes that are not application rows, such as tenant or organization roots:

```csharp
await db.ProvisionResourceWithIdAsync(
    $"org::{organization.Id}",
    "organization",
    organization.Name,
    parentResourceId: "root",
    cancellationToken: ct);
```

## How inheritance works

When checking `WORKSPACE_VIEW` on `workspace::1`:

1. Check grants directly on `workspace::1`.
2. Check grants on `org::acme`.
3. Check grants on `root`.
4. If any ancestor has a grant with a role that includes `WORKSPACE_VIEW`, access is allowed.

This means a single grant at the organization level can authorize resources underneath it without creating per-resource grants.

An inactive resource cuts the chain: a grant above it does not reach anything beneath it, and the inactive resource itself is denied.

## The lineage

Point checks and list filters read stored ancestry rather than traversing parents. Every resource carries its **lineage**, the tree's closure written on its own row: its ancestor at each level of the tree (`Ancestor0` is the top of its tree, `Ancestor1` the next level down, and so on, up to the configured `MaxResourceHierarchyDepth`; each holds the ancestor's compact key, `Seq`), its `Depth`, and its `Reach`, the highest level from which access flows down to it through active resources only. A resource that is inactive, lies beneath an inactive ancestor, lies in a cycle, or sits deeper than the configured depth has no reach, and is denied.

With the lineage, "is `workspace::1` under a grant on `org::acme`" is one comparison: `workspace::1`'s ancestor at level 1 is `org::acme`, and its reach includes level 1. One filtered index per level on the resources table (`IX_SqlOSFgaResources_Ancestor{level}`) answers "everything under `org::acme`" with one seek. [`CheckAccessAsync`](/docs/fga/checking-a-permission) applies the test to one resource in one query. [`BuildFilterAsync`](/docs/fga/list-filter#the-closure) uses both: for a caller who sees few rows it lists everything under the caller's grants through those indexes, and for one who sees many it runs the one-resource check on each row it reads. They agree row for row.

Two triggers on the resources table (after insert, after update of a parent or activity) keep the lineage exact. All of it lives on SqlOS's resources table: the columns, the per-level indexes and the triggers. Nothing is on your application tables.

| Operation | What SqlOS does | Cost |
|---|---|---|
| Create a resource | Computes its lineage from its parent | One row |
| Grant or revoke | Nothing; the next query reads the grant | No lineage work |
| Change a resource's type | Nothing; the type is a column of the row, read when a query runs | No lineage work |
| Move a resource to another parent | Recomputes the subtree beneath it, level by level | The subtree |
| Deactivate or reactivate a resource | Recomputes the reach of the subtree beneath it | The subtree |
| Delete a resource | Nothing; a resource with children cannot be deleted, so no other row's lineage depends on it | No lineage work |
| A move that would create a cycle, or place a resource deeper than the configured depth | Rejects the statement | — |
| First start on a database whose lineage was never built | Fills the lineage once: the internal nodes level by level, then every range of 500,000 resources in its own transaction | The whole table, once |

A bulk load of resources that skips triggers must fill the lineage itself or run the rebuild procedure afterwards (`sp_SqlOSFgaResources_LineageRebuild` on SQL Server, `fn_SqlOSFgaResources_LineageRebuild()` on PostgreSQL). The rebuild recomputes every row from `ParentId`, in ranges of 500,000 resources on SQL Server (each range its own transaction, so the log stays small at any size) and in one transaction on PostgreSQL. A rebuild that fails part-way is run again at the next start: SqlOS records the routines as current only after it completes. A bulk load of application rows needs nothing: a row is visible as soon as its `ResourceId` names a resource the caller may see.

## Changes made at the same time

SqlOS keeps the lineage correct when transactions change the tree concurrently, including on PostgreSQL and on SQL Server with read-committed snapshot (the Azure SQL default), where reads do not wait for writers. Every trigger that maintains the lineage takes one lock before it reads anything:

- **Inserts** of resources take it shared, so they run side by side.
- **Moves and activity changes** take it exclusively. Each waits for transactions that are already writing to commit, then computes from what they committed; inserts that start meanwhile wait for it.

Without the lock, a row inserted while its parent was being deactivated could stay visible, and two moves could together commit a cycle; the integration tests run those races on both databases.

Change resources in `READ COMMITTED` (the default for EF Core on both databases) or `SERIALIZABLE` transactions. A transaction that keeps reading the state it started with could compute from a tree another transaction has since changed, so SqlOS refuses tree changes inside one with a clear error: `REPEATABLE READ` on PostgreSQL, `SNAPSHOT` on SQL Server. Read-committed snapshot is `READ COMMITTED` and is fine. Writes to your own tables have no such rule.

A move or deactivation of a large subtree holds the exclusive lock while it rewrites the subtree, so inserts elsewhere wait for it to commit. Moves and deactivations are rare next to inserts; schedule bulk reorganizations of very large subtrees outside peak traffic.
